# 第 11 阶段逐次开发提示词

本文依据 `docs/44_第11阶段多仓库存管理开发文档.md` 和 `docs/46_第11阶段多仓库存管理Schema差距清单.md` 拆分。每次只复制一条提示词给 Codex。完成、测试并人工确认当前步骤后，再进入下一条。

## 使用方法

1. `docs/46` 已于 2026-07-27 完成复核；后续实现默认从“02. 新增多仓库存基础 Schema 与模式写入保护”开始。只有当前代码或 migration 已发生实质变化时才重新执行第 01 条。
2. 后续每次只复制一个代码块，不要一次发送多条。
3. 每步完成后先检查改动文件、测试结果、数据库变更和遗留风险。
4. 如果当前工作区已有未提交改动，必须保留并绕开，不能重置或覆盖。
5. 第 16 条以前只允许本地或隔离测试库验证，不连接生产库。

## 通用要求

- 开始前完整阅读 `docs/44_第11阶段多仓库存管理开发文档.md`；第 01 条完成后还要阅读 `docs/46_第11阶段多仓库存管理Schema差距清单.md`。
- 先检查 `git status`、相关 schema、migration、服务、测试和 Flutter 页面，基于当前事实修改，不假设文档中的计划已经实现。
- 技术栈保持 NestJS、Prisma/MySQL 和 Flutter，不引入第二套数据库或库存微服务。
- 库存流水是不可变事实，余额是可重建快照；禁止让 controller、订单 service 或脚本直接改余额绕过库存领域服务。
- 所有自动库存事件必须事务化、幂等并能抵抗并发；重复请求不能重复占用、出库、返库或调拨。
- 业务幂等必须使用规范化非空 `sourceKey`、`idempotencyKey` 和 `requestHash`；HTTP `requestId` 仅用于追踪。相同 key 不同内容必须稳定拒绝，不能依赖含可空字段的复合唯一键。
- 当前通用商品 PATCH 不得继续自由切换库存模式；模式切换必须使用专用状态机和 `expectedCurrentMode`。有库存流水后不得切回 `NONE`，`QUANTITY/SERIALIZED` 不得在线直接互转。
- 订单库存占用必须使用服务端稳定的 `inventoryLineKey`，不能直接使用更新时会 delete/recreate 的 `SalesOrderItem.id`。
- 所有订单库存钩子必须明确排除现有 `orderType=AFTER_SALES` 的财务负向销售订单；补发/换货只能通过独立履约命令触发。
- 所有数量使用整数瓶；金额使用整数分；生产批次、批次序号、采购单号和物流码使用字符串，保留前导零。
- 普通 `QUANTITY` 商品允许负库存并产生预警；茅台 `SERIALIZED` 商品不足时记录待配瓶，禁止伪造逐瓶数据。
- 销售不能看到任何库存数量；库管不能看到采购成本；财务可维护库存采购成本但不能直接调数量；老板可查看本阶段库存成本并审批盘点；管理员拥有全部权限。
- 老板的库存成本权限不得顺便扩大到现有商品实际成本、扣单、提成和旅行社成本接口。
- 不改变现有 `ProductActualCost`、订单成本快照和毛利历史口径；采购批次成本只用于库存追踪和库存金额。
- 新接口、导出、操作日志、异常详情和测试快照都必须验证字段级防泄露。
- 普通订单和售后 DTO 必须按 actor 显式投影；不能依赖 OperationLog sanitizer 自动屏蔽成本、库存数量或瓶码。
- 不向公开二维码销售单、销售角色、AI 助手或无权导出泄露仓库、库存、瓶码内部状态或成本。
- 新增或修改关键业务时补充操作日志、稳定错误码、后端单元/接口测试和 Flutter 测试。
- 每步结束运行与改动范围相称的 `prisma format`、`prisma validate`、`prisma generate`、后端测试、`npm run build`、`flutter analyze` 和 `flutter test`；无法运行时说明原因，不得伪造结果。
- 不连接或写入生产库。只有第 16 条在明确确认隔离测试库、备份和目标版本后，才允许执行云端写入型验证。
- 生产仓库名称、唯一默认仓、阈值、`goLiveAt` 和预警 SLA 只属于上线配置，不得阻止本地 Schema、领域服务和测试 fixture 开发，也不得硬编码到 migration/seed。
- 完成后报告：改动文件、数据库变化、测试命令及结果、未解决风险、下一步建议。不要自动提交、推送或部署，除非用户另行明确要求。

## 01. 复核现状并生成 Schema 差距清单

```text

重点复核：
1. Product.inventoryTrackingMode 当前是否只有 NONE/SERIALIZED，普通商品如何安全切换为 QUANTITY。
2. 当前是否已有 Warehouse、仓库商品余额、库存批次、库存单据、流水、占用、调拨、盘点和预警模型。
3. SalesOrder/SalesOrderItem 当前如何表达履约仓库、配送方式、打包状态、订单修改和取消，哪些服务路径会触发保存或更新。

5. SerializedInventoryUnit 当前状态、订单绑定、成本权限和销售选码流程，迁移到多仓与库管配瓶需要哪些兼容处理。

7. 当前数据库和服务是否具备事务、幂等键、并发条件更新和余额重建能力。
8. 历史订单、未打包订单和现有逐瓶库存上线切换需要哪些 dry-run 脚本。

差距清单必须包含：
- 当前代码事实和准确文件位置。
- 建议模型、字段、枚举、唯一约束、索引和外键。
- 每项迁移的数据兼容及回滚边界。
- 订单、售后、茅台、权限、导出、日志和 UI 的影响面。
- 分阶段实现顺序及每阶段测试要求。
- 仍需人工确认的仓库名称、默认仓库和预警阈值只能列为上线配置，不得阻止本地架构开发。

只新增或更新 docs/46，不修改 schema、migration、业务代码、测试和其他文档。完成后报告发现的高风险点和是否建议调整后续提示词。
```

## 02. 新增多仓库存基础 Schema 与模式写入保护

```text
请根据 docs/44 和 docs/46 实现第 11 阶段第一批 expand 型 Prisma Schema、migration 和库存模式写入保护。只建立可独立验证的库存底座，不接销售订单自动扣减，不开发 Flutter。

至少覆盖：
1. InventoryTrackingMode 增加 QUANTITY，保留 NONE/SERIALIZED 兼容。
2. SerializedInventoryStatus 先增加 RESERVED/OUTBOUND/UNAVAILABLE，但保留 ALLOCATED；本步不转换历史状态、不删除旧值。
3. Warehouse 与 InventoryConfiguration：编号、规范化名称、地址、负责人、启用状态、默认仓、goLiveAt/policyVersion/maintenanceMode 和审计字段。用 activeDefaultKey 可空唯一 + CHECK，或单行配置表 defaultWarehouseId + 事务锁，保证最多一个启用默认仓。
4. WarehouseProductStock：warehouseId + productId 唯一，保存 onHandQty、reservedQty、unavailableQty、inTransitQty、version、lastMovementId 和审计时间；reserved/unavailable/inTransit 不得为负，onHand 可为负。
5. InventoryBatch：仓库、商品、来源单据行、供应商、采购单号、生产批次、生产日期、入库量、剩余量、不可售量、进货单价分、成本状态、fifoAt、sourceLineKey 唯一、version 和审计字段；字符串保留前导零。
6. InventoryDocument 与 InventoryDocumentLine：支持期初、采购、顾客退货、盘盈、其他入库、销售出库、盘亏、其他出库、调拨出入、不可售调整和冲销；明确 DRAFT/POSTED/REVERSED。
7. InventoryMovement：不可变流水，至少保存非空 sourceKey 唯一、单据行、仓库、商品、可选批次/逐瓶、movementType、onHand/reserved/unavailable/inTransit 四类 delta、业务时间、操作者、冲销来源和必要快照。
8. InventoryCommandReceipt：idempotencyKey 唯一、commandType、requestHash、status、resultDocumentId、actor 和时间。
9. InventoryReservation：按订单稳定 inventoryLineKey、履约仓和商品保存 requested/reserved/assigned/outbound 数量、状态、version 和非空 sourceKey。
10. InventoryTransfer、InventoryTransferLine 和可分次 InventoryTransferReceipt/Line，或能等价表达调出、在途、部分实收和差异的模型。
11. StockAlertConfig：warehouseId + productId 唯一，最低库存和启用状态。
12. SalesOrder 增加可空 fulfillmentWarehouseId、inventoryAppliedAt、inventoryPolicyVersion、inventoryVersion 等兼容字段；SalesOrderItem 增加可空但对新库存明细必须稳定唯一的 inventoryLineKey。
13. SerializedInventoryUnit 增加可空 warehouseId、inventoryBatchId、version 等兼容字段，先保持历史数据可迁移。
14. 补齐 Product、Warehouse、User、SalesOrder、SalesOrderItem、SerializedInventoryUnit 与库存事实的关系、索引和 Restrict/SetNull 策略；业务事实不允许 Cascade 删除，人员审计可 SetNull 并保留快照。

约束：
- migration 不得直接把生产商品全部改为 QUANTITY，不得猜默认仓库，不得回填历史订单或逐瓶数据。
- 当前 Product 通用 create/update 不得因枚举扩展而允许现有商品自由切换模式。禁止通用 PATCH 修改已有商品的 inventoryTrackingMode，或至少在专用状态机完成前稳定拒绝任何实际模式变化；新商品默认 NONE。
- 模式切换专用命令和 apply 脚本留到后续步骤实现，但 Schema 要能保存 expectedCurrentMode、启用边界和审计所需事实。
- 不用包含可空 batchId/unitId/sourceLineId 的复合唯一键代替非空 sourceKey。
- 不物理删除有流水引用的仓库、商品、批次、单据。
- 不修改现有订单成本、毛利、提成和积分字段。
- 如果 MySQL 无法可靠用普通唯一索引保证单默认仓库，明确采用事务 + 锁/配置表等可测试策略，不能只靠前端。
- migration 必须 DB-first，旧应用能够忽略新增表/可空列；MySQL enum metadata lock 要在说明中列出隔离库演练要求。

验证：
- prisma format、validate、generate。
- migration SQL 人工检查测试。
- 扩展现有 schema smoke tests，验证模型、枚举、CHECK、非空 sourceKey、唯一约束、外键、索引及 ALLOCATED 仍存在。
- 测试 Product 通用 PATCH 不能切换已有商品库存模式。
- 测试并发设置默认仓只能有一个成功。
- npm run build 和现有后端测试回归。
```

## 03. 实现库存记账核心与余额重建

```text
请实现独立的 inventory 后端领域模块和库存记账核心。本步不接销售订单、不做 Flutter 页面。

要求：
1. 新增 Nest module/controller/service/repository 或符合当前项目风格的等价结构，所有余额变化只能经过库存领域服务。
2. 事务内按固定顺序：抢占 InventoryCommandReceipt 并校验 requestHash；锁定或用 version 条件更新 Stock/Batch/Reservation/Unit；写 Document/Line 与不可变 Movement；更新余额/批次快照；写角色安全 OperationLog。
3. 所有事件使用规范化非空 sourceKey；相同 idempotencyKey + 相同 requestHash 返回已有结果，相同 key + 不同 hash 返回稳定冲突错误。HTTP requestId 只记录追踪关系。
4. QUANTITY 商品允许 onHand/available 为负；reservedQty、unavailableQty 和 inTransitQty 不得为负。
5. SERIALIZED 商品不能通过普通数量接口直接增减，必须走逐瓶适配层；NONE 商品拒绝库存写入。
6. 实现占用、释放占用、正式出库、入库、调拨在途、不可售转移、冲销的内部命令接口，明确每个命令对 onHand/reserved/unavailable/inTransit 的影响。
7. 实现按仓库+商品从有效流水重建余额的只读校验和管理员修复预览；本步不得自动覆盖不一致余额。
8. 并发使用数据库事务和条件更新/版本号，避免 lost update。
9. 所有生效与冲销写 OperationLog；日志 DTO 按角色裁剪成本。
10. 库存计算不受全局 financeMark 查询开关影响。
11. Todo、预警和读模型刷新只能在库存事实提交后触发，并具备补偿机制；其失败不能导致库存命令被不安全重放。
12. 已生效流水禁止 UPDATE/DELETE；冲销关系一对一唯一，同一事实不能冲销两次。

测试至少覆盖：
- 正常入库、出库、占用、释放、不可售转换和冲销。
- 负库存允许并正确计算 shortage。
- reserved/unavailable/inTransit 不能变负。
- 重复请求幂等、同 key 不同 hash 冲突、sourceKey 唯一、两个并发请求不丢更新。
- NONE/QUANTITY/SERIALIZED 模式隔离。
- 流水重建值与余额、批次快照一致，修复预览零写入。
- 事务任一步失败时单据、流水和余额全部回滚。
- Todo/读模型刷新失败不重复生成库存事实。

完成后运行相关后端测试、npm run build，并更新 docs/46 的已完成/剩余差距，不开发前端。
```

## 06. 实现库存调拨和不可售管理

```text
请实现多仓调拨、调拨在途和不可售库存管理。

要求：
1. 调拨单按来源仓、目标仓和商品明细创建；来源与目标不能相同。
2. 调出确认后从来源仓 onHand 扣减并增加统一在途事实/快照；目标仓确认收到后减少在途并增加目标仓 onHand。
```
