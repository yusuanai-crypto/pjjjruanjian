# 第 3 阶段旅行团管理开发文档

版本：v0.1
状态：字段口径已按业务反馈固化，进入开发前如有调整，先改本文再改代码。
测试环境基线：第 1 + 第 2 阶段已完成云服务器测试验收，当前 API 地址为 `http://47.120.24.23`。

## 1. 阶段目标

第 3 阶段目标是把“旅行团管理”从当前的部分接口和页面骨架，推进到可在测试环境真实录入、查询、补充、标记和按角色验收的业务模块。

本阶段完成后应具备：

- 前台可创建旅行团。
- 团号由系统自动生成，不允许手工输入。
- 导游库必须落地，录旅行团时必须从导游库选择导游。
- 品鉴师必须从员工账号中选择，且角色必须为 `taster`。
- 车牌号、品鉴馆号、人数等关键接待字段按固定口径校验。
- 品酒种类/瓶数使用明细结构，不再只放备注。
- 待处理旅行团按规则自动生成。
- 财务可标记旅行团；财务标记后再修改字段，只记录日志，不自动取消标记。
- 老板只查看旅行团，不允许修改。

## 2. 本阶段不做的事

- 不做完整客户库、商品库和订单业务闭环；订单仍按当前已有接口能力对接。
- 不做真实二维码销售单生成。
- 不做完整提成和积分规则计算。
- 不做库管、售后进入旅行团管理。
- 不做 AI 查询旅行团数据。
- 不把“待处理旅行团”做成人工维护表，先按规则自动计算。

## 3. 核心业务对象

### 3.1 旅行团主记录

旅行团主记录是第 3 阶段主业务对象，建议继续使用 `TravelGroup` 作为主表和主接口承载。

### 3.2 导游库

导游库必须在第 3 阶段马上落地。旅行团录入时必须先选择导游；导游不存在时，先新建导游，再录旅行团。

旅行团保存时需要保存导游快照字段，避免后续导游资料变更影响历史记录。

### 3.3 品鉴师关联

品鉴师必须从员工账号中选择：

- 只能选择角色为 `taster` 的启用员工。
- 旅行团保存 `tasterId`。
- 同时保存 `tasterName` 快照。
- 品鉴师登录后可查看本人全部接待团、今天及未来本人对接团、今天未进店团和全部未来团。

### 3.4 品酒明细

品酒种类/瓶数必须做明细，不放在备注里。第 3 阶段可以先不接商品库，酒品名称允许文本录入，但数据结构必须按明细保存。

### 3.5 待处理旅行团

待处理旅行团按规则自动生成，先不做人工维护表。页面和接口可以返回计算出来的 `pendingStatus` 和 `pendingReasons`。

### 4.2 团号生成规则

团号由系统自动生成，不允许手填。

建议规则：

```text
TG + yyyyMMdd + 当日 3 位流水
示例：TG20260627001
```

规则要求：

- 按 `visitDate` 生成当日流水。
- 同一天从 `001` 开始递增。
- 数据库必须有唯一约束。
- 并发创建时必须在事务中生成，避免重复团号。
- 如果未来需要门店前缀，可扩展为 `TG + 门店码 + yyyyMMdd + NNN`，第 3 阶段先不加门店码。

### 4.3 团型枚举

团型固定为：

```text
KB团
AB团
保险团
渠道团
散客团
其他
```

如果选择“其他”，前端必须提示填写备注。

## 5. 待处理规则定版

待处理旅行团按规则自动生成，不手动维护。

满足以下任一条件，进入待处理：

| 规则 | 待处理状态 | 说明 |
| --- | --- | --- |
| 缺少品鉴师 | `pending_front_desk` | 原则上新建时已强校验，此规则用于历史数据或异常数据 |
| 缺少导游姓名、导游手机号、旅行社或人数 | `pending_front_desk` | 导游库和人数必须补齐 |
| 无订单且品鉴师总结未填写 | `pending_taster` | 品鉴师需要补接待总结 |
| 财务未标记，且超过当天结束时间 | `pending_finance` | 财务需要确认 |
| 系统检测异常 | `abnormal` | 如人数为 0、团号重复、离店早于进店 |

明确不作为待处理条件：

- 缺少离店时间。
- 已有订单但旅行团未补离店备注。

待处理状态建议：

```text
pending_front_desk   前台待补充
pending_taster       品鉴师待总结
pending_finance      财务待确认
abnormal             数据异常
completed            已完成
```

接口建议同时返回：

```json
{
  "pendingStatus": "pending_taster",
  "pendingReasons": ["无订单且品鉴师总结未填写"]
}
```

## 6. 财务标记规则

财务标记字段为 `financeMark`，默认 `false`。

固定规则：

- 财务、管理员可标记或取消标记。
- 标记或取消标记后记录本次操作的 `markedById`、`markedAt`。
- 当前是否已标记只以 `financeMark` 判断；`markedById`、`markedAt` 只表示最后一次标记操作审计信息。
- 财务标记后再修改字段，只记录日志，不自动取消标记。
- 日志必须记录修改人、修改时间、修改字段、修改前、修改后。
- 页面建议显示“已财务标记后发生过修改”的提示，但不改变 `financeMark` 值。
- 全局“只查询已标记信息”开启后，旅行团查询只返回 `financeMark = true` 的记录。

关键字段建议包括：

```text
visitDate
travelAgency
licensePlate
guideId
guideName
guidePhone
guestCount
tastingRoomNo
tasterId
tasterName
arrivalTime
departureTime
groupType
tastingItems
remarks
tasterSummary
```

## 7. 角色权限定版

| 角色 | 可看 | 可改 |
| --- | --- | --- |
| 管理员 | 全部旅行团 | 全部字段 |
| 老板 | 全部旅行团 | 不可修改 |
| 前台 | 权限内旅行团 | 基础接待字段、导游、车牌、馆号、人数 |
| 销售 | 权限内旅行团 | 人数、品酒明细、离店时间、销售备注 |
| 品鉴师 | 本人全部接待团；今天及未来本人对接团；今天未进店团；全部未来团 | 今天可修改本人接待或对接团；未来仅可修改本人对接团；历史团只读；字段仍限品鉴师白名单 |
| 财务 | 全部或财务范围内旅行团 | 财务标记、财务备注 |
| 库管 | 不进入旅行团管理 | 不可修改 |
| 售后 | 不进入旅行团管理 | 不可修改 |

品鉴师权限统一按 `Asia/Shanghai` 自然日计算。“今天未进店”仅指 `arrivalTime` 为 null 或空字符串。列表 Prisma 条件、单条详情、附件下载、`canEditByCurrentUser`、旅行团 PATCH、总结及附件上传/删除必须复用同一策略；全局“只查询已标记信息”开启后再与 `financeMark = true` 取交集。扩大旅行团读取范围不扩大订单、客户或财务权限，公共可读团对无关联品鉴师不返回订单明细。

老板规则单独强调：

- 老板可以查询全部旅行团。
- 老板可以进入旅行团详情。
- 老板不允许新增、修改、删除、财务标记。

## 8. 数据库开发拆分

### 8.1 优先复核现有表

开发前先复核当前 Prisma schema 中已有的：

- `TravelGroup`
- `GuideCarriedGroup`
- `PendingTravelGroup`
- `SalesOrder`
- `OperationLog`

目标是尽量兼容现有测试数据，不做无意义重建。

### 8.2 建议新增或调整

优先级从高到低：

1. 新增导游库表 `guides`。
2. `travel_groups` 增加 `guide_id`、`taster_summary`、`taster_summary_at`、`created_by_id`、`updated_by_id` 等缺失字段。
3. 新增旅行团品酒明细表 `travel_group_tasting_items`。
4. 为 `travel_groups.group_no` 增加唯一约束。
5. 为查询字段增加索引：`visit_date`、`guide_id`、`taster_id`、`finance_mark`、`group_type`。
6. 如已有字段类型不满足口径，按兼容方式迁移，不直接删除旧字段。

### 8.3 迁移原则

- migration 必须可在测试环境 `prisma migrate deploy` 执行。
- 不能覆盖已有测试环境数据。
- 对旧数据缺必填字段的情况，先允许为空并通过待处理规则暴露，后续再逐步加严格约束。
- 新建记录必须按新规则严格校验。
- seed 需要补至少一条完整旅行团、一个导游、一个品鉴师账号和一组品酒明细。

### 11.1 数据库拆分明细

数据库优先处理结构稳定性，顺序如下：

1. 复核现有 `TravelGroup` 字段。
   - 记录当前已有字段：团号、到店日期、旅行社、车牌号、导游姓名/电话、人数、品鉴馆号、品鉴师姓名、进店时间、团型、`wineDetails`、离店时间、备注、金额/积分、财务标记、`tasterId`、创建/更新人。
   - 明确差距字段：`guideId`、`tasterSummary`、`tasterSummaryAt`。
   - 可选差距字段：`postMarkEditedAt`、`postMarkEditedById`，用于前端提示“财务标记后发生过修改”。
   - 产出：schema 差距清单，不先写 migration。

2. 新增 `guides` 表。
   - 字段：`id`、`name`、`phone`、`travelAgency`、`remarks`、`isActive`、`createdAt`、`updatedAt`。
   - 约束：`phone` 建议唯一，`name`、`phone`、`travelAgency` 必填。
   - 索引：`phone`、`name`、`travelAgency`、`isActive`。
   - 产出：导游库 migration 和 seed。

3. 给 `travel_groups` 增加导游关联。
   - 新增 `guide_id`，关联 `guides.id`，旧数据允许为空。
   - 保留 `guide_name`、`guide_phone`、`travel_agency` 快照字段。
   - 新建旅行团时必须有 `guideId`，并从导游库写入快照。
   - 产出：兼容旧数据的 migration。

4. 新增 `travel_group_tasting_items` 明细表。
   - 字段：`id`、`travelGroupId`、`productName`、`quantity`、`unit`、`note`、`sortOrder`、`createdAt`、`updatedAt`。
   - 约束：`travelGroupId`、`productName`、`quantity`、`unit` 必填；`quantity > 0` 在后端校验。
   - 旧字段 `wineDetails` 保留兼容，后续不作为新数据主路径。
   - 产出：品酒明细 migration。

5. 团号唯一约束和生成规则。
   - 当前 `groupNo` 已唯一，继续保留。
   - 新建接口不再接收前端 `groupNo`。
   - 后端按 `visitDate` 在事务中生成 `TGyyyyMMddNNN`。
   - 并发冲突时依靠唯一约束兜底，后端可重试一次。
   - 产出：团号生成 helper 和并发/重复测试。

6. 旧测试数据兼容。
   - 不立刻把旧字段改成数据库 `NOT NULL`。
   - 新建记录走严格校验；旧数据缺字段时进入待处理或异常。
   - 从旧 `guideName + guidePhone + travelAgency` 尝试生成导游库记录。
   - 旧 `wineDetails` 可保留；如结构简单，可迁移为一条品酒明细。
   - 现有 `PendingTravelGroup` 表先保留，但第 3 阶段新接口不再把它作为主数据源。

### 11.2 后端 API 拆分明细

后端先保证数据结构和权限正确，再接 Flutter。

1. 导游库接口。
   - `GET /api/guides`：管理员、前台、销售、财务可访问，支持 keyword、travelAgency、isActive。
   - `POST /api/guides`：管理员、前台可新建。
   - `GET /api/guides/:id`：管理员、前台、销售、财务可访问。
   - `PATCH /api/guides/:id`：管理员、前台可修改。
   - `POST /api/guides/:id/disable`：管理员可停用。
   - `POST /api/guides/:id/enable`：管理员可启用。
   - 每个写接口写 `operation_logs`。

2. 品鉴师选择接口。
   - `GET /api/users/tasters`：管理员、前台、销售、财务可访问。
   - 只返回启用的 `taster` 员工。
   - 返回字段限制为 `id`、`name`、`username`，不暴露员工管理细节。

3. 旅行团新增接口。
   - `POST /api/travel-groups`：管理员、前台可访问。
   - 不接收 `groupNo`，由系统生成。
   - 校验车牌号、品鉴馆号、旅行社、导游、人数、品鉴师、团型。
   - 校验 `tasterId` 必须是启用的品鉴师账号。
   - 从 `guideId` 写入导游快照。
   - 在一个事务中保存旅行团和品酒明细。
   - 写 `operation_logs`。

4. 旅行团查询接口。
   - `GET /api/travel-groups`：管理员、老板、前台、销售、财务、品鉴师可访问。
   - 支持 `dateFrom/dateTo`、`keyword`、`groupNo`、`guideId`、`tasterId`、`groupType`、`financeMark`、`pendingStatus`、`limit`。
   - 老板、管理员、财务看全量或财务范围。
   - 品鉴师读取范围为：`tasterId = 当前用户`（全部日期），`liaisonTasterId = 当前用户`（今天及未来），今天 `arrivalTime` 为 null 或空字符串的团，以及全部未来团。
   - 销售只看自己创建或和自己订单相关的旅行团。
   - 全局标记查询开启后，只返回 `financeMark = true`。

5. 旅行团详情接口。
   - `GET /api/travel-groups/:id`：管理员、老板、前台、销售、财务、品鉴师可访问。
   - 返回基础信息、导游快照、品鉴师、品酒明细、订单概要、待处理状态和原因、财务标记状态。
   - 按角色执行数据范围校验，不允许通过 ID 越权读取。

6. 旅行团修改接口。
   - `PATCH /api/travel-groups/:id`：管理员、前台、销售、品鉴师、财务可访问，但字段权限不同。
   - 管理员：全部字段。
   - 前台：基础接待字段、导游、车牌、馆号、人数、品鉴师、进店时间、团型、备注、品酒明细。
   - 销售：人数、品酒明细、离店时间、销售备注。
   - 品鉴师：人数、接待总结、品鉴相关备注。
   - 财务：财务备注类字段；财务标记走独立接口。
   - 老板、库管、售后：不可修改。
   - 财务标记后修改字段，只写日志，不自动取消 `financeMark`。

7. 财务标记接口。
   - `PATCH /api/travel-groups/:id/finance-mark`：管理员、财务可访问。
   - 修改 `financeMark`、`markedById`、`markedAt`。
   - 写操作日志。

8. 品鉴师总结接口。
   - `POST /api/travel-groups/:id/taster-summary`：管理员、对应品鉴师可访问。
   - 品鉴师今天可提交本人接待或对接团总结，未来仅本人作为对接品鉴师时可提交，历史团不可提交。
   - 保存 `tasterSummary`、`tasterSummaryAt`。
   - 写操作日志。

9. 待处理旅行团自动计算接口。
   - `GET /api/pending-travel-groups`：管理员、老板、前台、销售、财务、品鉴师可访问。
   - 不再以 `pending_travel_groups` 表作为主数据源。
   - 从 `travel_groups` 按规则计算 `pendingStatus` 和 `pendingReasons`。
   - 去掉两个规则：缺离店时间、已有订单但未补离店备注。
   - 保留规则：缺品鉴师；缺导游姓名/手机号/旅行社或人数；无订单且品鉴师总结未填；财务未标记且超过当天结束时间；数据异常。
