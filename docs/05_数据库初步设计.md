# 数据库初步设计

本文设计第一版数据库。目标是：够业务上线使用，字段清楚，关系清楚，不一开始做得过度复杂。

数据库推荐：PostgreSQL  
时间统一：北京时间 `Asia/Shanghai`  
金额单位：建议用“分”存储，例如 199 元存成 19900，避免小数误差。

## 1. 设计原则

### 1.1 原始业务数据不能随便覆盖

例如订单金额、客户电话、旅行团人数，这些都可能影响财务和统计。重要修改要记录操作日志。

为什么：

后期如果数据对不上，需要知道是谁在什么时候改了什么。

### 1.2 客户、订单、旅行团要分开

- 旅行团是接待来源。
- 客户是购买的人。
- 订单是客户某一次购买记录。
- 标记信息是财务确认状态，旅行团和客户默认都是 0，由财务改为 1。

为什么：

一个旅行团可以有多个客户购买，一个客户也可能以后复购。分开设计后，查询和统计更准确。

### 1.3 标记信息由后端统一控制查询

老板或前台开启“只查询已标记信息”后，后端所有普通查询、统计和 AI 查询都必须过滤标记信息为 1 的旅行团和客户。

为什么：

不能只在 App 页面隐藏未标记数据。只在前端隐藏不安全，后端统一过滤才能保证所有角色、导出、统计和 AI 查询口径一致。

### 1.4 提成和积分要留记录

提成规则可能会变，但历史订单应保留当时计算出来的结果。

为什么：

如果只保存规则不保存计算结果，以后规则变了，历史提成可能被重新算错。

## 2. 用户表 `users`

用途：

保存员工账号、角色和登录信息。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| name | text | 员工姓名 |
| username | text | 登录账号 |
| password_hash | text | 加密后的密码 |
| role | text | 角色 |
| phone | text | 手机号 |
| leader_id | uuid | 销售组长，可为空 |
| is_active | boolean | 是否启用 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

角色建议：

- admin
- boss
- front_desk
- sales
- finance
- warehouse
- after_sales
- taster

为什么要有 `leader_id`：

销售组长提成需要知道销售归属哪个组长。

## 3. 旅行社表 `travel_agencies`

用途：

保存旅行社基础信息。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| name | text | 旅行社名称 |
| contact_name | text | 联系人 |

## 4. 旅行团表 `travel_groups`

用途：

保存每个进店旅行团信息。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| group_no | text | 团号 |
| visit_date | date | 日期 |
| agency_id | uuid | 旅行社 |
| bus_plate_no | text | 车牌号 |
| guide_name | text | 导游 |
| guide_phone | text | 导游电话 |
| guest_count | integer | 人数 |
| tasting_room_no | text | 品鉴馆馆号 |
| taster_id | uuid | 品鉴师，对应 users |
| entry_time | timestamp | 进店时间 |
| leave_time | timestamp | 离店时间，可为空 |
| wine_tasting_summary | text | 品酒种类和瓶数 |
| group_type | text | 团型，例如 KB团、保险团、渠道团 |
| finance_mark | smallint | 标记信息，默认 0，财务可改为 1 |
| marked_by | uuid | 标记操作人，可为空 |
| marked_at | timestamp | 标记时间，可为空 |
| notes | text | 备注 |
| created_by | uuid | 创建人 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

建议唯一规则：

- `group_no` 尽量唯一。
- 如果业务上团号可能重复，则使用 `group_no + visit_date` 防重复。

为什么这样设计：

旅行团是统计品鉴师接待数量、人数、打蛋率和团均销售额的基础。

必填说明：

- `bus_plate_no`、`guide_name`、`guide_phone` 为必填。
- `leave_time` 为可选，销售可以在接待结束后补充。
- 销售可以补充或修改 `wine_tasting_summary`、`notes`、`leave_time`。

为什么增加 `finance_mark`：

旅行团刚录入时默认未确认，标记为 0。财务核对后改为 1。老板或前台开启全局标记查询后，普通查询只展示标记为 1 的旅行团。

## 7. 订单明细表 `sales_order_items`

用途：

保存一个订单中具体买了哪些酒。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| order_id | uuid | 所属订单 |
| product_name | text | 酒品名称 |
| quantity | integer | 数量 |
| unit_price_cents | integer | 单价，单位分 |
| subtotal_cents | integer | 小计，单位分 |
| notes | text | 备注 |

为什么要有订单明细：

## 10. 旅行社返点比例规则表 `agency_rebate_rules`

用途：

保存旅行社日返、月返比例，数据来源参考 `旅行社返点比例和扣单规则.xlsx` 的“旅行社返点比例”。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| agency_id | uuid | 旅行社 |
| daily_rebate_rate | numeric | 日返积分比例 |
| monthly_rebate_rate | numeric | 月返积分比例，可为空 |
| total_rebate_rate | numeric | 合计比例，可为空 |
| is_active | boolean | 是否启用 |
| effective_from | date | 生效开始日期 |
| effective_to | date | 生效结束日期，可为空 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

旅行社积分计算：

- 旅行社扣酒成本 = 按旅行社和酒品匹配 `agency_deduction_rules` 后汇总。
- 旅行社上单金额 = 销售额 - 旅行社扣酒成本。
- 日返金额 = 旅行社上单金额 * 日返积分比例。
- 月返金额 = 旅行社上单金额 * 月返积分比例。

## 12. 员工提成规则表 `commission_rules`

用途：

配置销售提成、外联提成、组长提成等员工提成比例。旅行社积分不放在这张表里。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| rule_name | text | 规则名称 |
| target_type | text | 适用对象 |
| rate | numeric | 比例 |
| is_active | boolean | 是否启用 |
| effective_from | date | 生效开始日期 |
| effective_to | date | 生效结束日期，可为空 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

`target_type` 建议：

- sales_commission：销售提成，默认 0.02
- outreach_commission：外联提成，默认 0.008

品鉴师提成说明：

## 19. 全局标记查询规则

当 `system_settings.only_show_marked_records = true` 时：

- 旅行团查询只返回 `travel_groups.finance_mark = 1` 的记录。
- 客户查询只返回 `customers.finance_mark = 1` 的记录。
- 订单查询只返回关联客户和关联旅行团都已标记为 1 的记录。
- 品鉴师统计、老板看板、财务导出、AI 查询都使用同样过滤规则。
- 管理员恢复开关后，系统按角色权限正常查询。

为什么这样设计：

全局标记按钮影响的是全公司查询口径，所以必须在数据库查询层统一处理，不能每个页面各写一套判断。

## 20. 统计口径

### 出单销售额

有效订单金额合计。

建议包含：

- `order_status = valid`
- `order_status = partial_refund` 时按扣除退款后的金额计算

### 退单销售额

售后单中已完成退款或退单的金额合计。

### 总销售额

出单销售额 - 退单销售额。

### 总接待团数

指定时间范围内的旅行团数量。

### 总接待人数

指定时间范围内旅行团人数合计。

### 团均销售额

总销售额 / 总接待团数。

### 人均销售额

总销售额 / 总接待人数。

### 打蛋率

没有产生有效订单的旅行团数量 / 总接待旅行团数量。

为什么统计口径要写在数据库设计里：

后端开发、财务验收、老板看报表都要按同一套口径，否则每个人看到的数据会不一样。

## 21. 第一版索引建议

常用查询字段需要加索引：

- `travel_groups.visit_date`
- `travel_groups.group_no`
- `travel_groups.taster_id`
- `travel_groups.finance_mark`
- `sales_orders.order_date`
- `sales_orders.order_no`
- `sales_orders.customer_id`
- `sales_orders.travel_group_id`
- `sales_orders.sales_user_id`
- `sales_orders.delivery_type`
- `sales_orders.logistics_method`
- `sales_orders.packing_status`
- `sales_orders.logistics_no`
- `customers.phone`
- `customers.finance_mark`
- `after_sales_orders.order_id`

为什么需要索引：

数据少的时候查什么都快。数据多起来后，如果没有索引，按电话查客户、按日期查订单会变慢。
