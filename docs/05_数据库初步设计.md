# 数据库初步设计

本文设计第一版数据库。目标是：够业务上线使用，字段清楚，关系清楚，不一开始做得过度复杂。

数据库推荐：MySQL  
时间统一：北京时间 `Asia/Shanghai`  
金额单位：建议用“分”存储，例如 199 元存成 19900，避免小数误差。

MySQL 约定：

- 字符集使用 `utf8mb4`，排序规则建议 `utf8mb4_0900_ai_ci`。
- 表引擎使用 `InnoDB`，支持事务和外键。
- 主键用字符串 UUID，在 Prisma 中使用 `String @id @default(uuid()) @db.Char(36)`。
- 日期用 `DateTime @db.Date`，时间用 `DateTime @db.DateTime(0)`。
- 金额统一用 `Int` 存“分”，比例用 `Decimal @db.Decimal(10, 4)`。
- JSON 数据用 MySQL `Json` 类型。
- 后端连接字符串建议使用：`mysql://用户名:密码@服务器地址:3306/jiangjiu`。

## 1. 设计原则

### 1.1 原始业务数据不能随便覆盖

例如订单金额、客户电话、旅行团人数，这些都可能影响财务和统计。重要修改要记录操作日志。

为什么：

后期如果数据对不上，需要知道是谁在什么时候改了什么。

### 1.2 客户、订单、旅行团要分开

- 旅行团是接待来源。
- 客户是购买的人。
- 订单是客户某一次购买记录。
- 标记信息是财务确认状态，旅行团和客户默认都是 0，由财务改为 1。

为什么：

一个旅行团可以有多个客户购买，一个客户也可能以后复购。分开设计后，查询和统计更准确。

### 1.3 标记信息由后端统一控制查询

老板或前台开启“只查询已标记信息”后，后端所有普通查询、统计和 AI 查询都必须过滤标记信息为 1 的旅行团和客户。

为什么：

不能只在 App 页面隐藏未标记数据。只在前端隐藏不安全，后端统一过滤才能保证所有角色、导出、统计和 AI 查询口径一致。

### 1.4 提成和积分要留记录

提成规则可能会变，但历史订单应保留当时计算出来的结果。

为什么：

如果只保存规则不保存计算结果，以后规则变了，历史提成可能被重新算错。

## 4. 旅行团表 `travel_groups`

用途：

保存每个进店旅行团信息。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| group_no | text | 团号 |
| visit_date | date | 日期 |
| agency_id | uuid | 旅行社 |
| bus_plate_no | text | 车牌号 |
| guide_id | uuid | 导游，对应 guides |
| guest_count | integer | 人数 |
| tasting_room_no | text | 品鉴馆馆号 |
| taster_id | uuid | 品鉴师，对应 users |
| entry_time | timestamp | 进店时间 |
| leave_time | timestamp | 离店时间，可为空 |
| wine_tasting_summary | text | 品酒种类和瓶数 |
| taster_review_summary | text | 品鉴师接待总结，可为空 |
| taster_review_submitted_at | timestamp | 品鉴师首次提交总结时间，可为空 |
| taster_review_updated_at | timestamp | 品鉴师最后修改总结时间，可为空 |
| group_type | text | 团型，例如 KB团、保险团、渠道团 |
| finance_mark | smallint | 标记信息，默认 0，财务可改为 1 |
| marked_by | uuid | 标记操作人，可为空 |
| marked_at | timestamp | 标记时间，可为空 |
| notes | text | 备注 |
| created_by | uuid | 创建人 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

建议唯一规则：

- `group_no` 尽量唯一。
- 如果业务上团号可能重复，则使用 `group_no + visit_date` 防重复。

为什么这样设计：

旅行团是统计品鉴师接待数量、人数、打蛋率和团均销售额的基础。

必填说明：

- `bus_plate_no`、`guide_id` 为必填。
- 导游姓名和导游电话在 `guides` 表中维护，新增旅行团时选择已有导游；如果导游不存在，先新增导游。
- `leave_time` 为可选，销售可以在接待结束后补充。
- 销售可以补充或修改 `wine_tasting_summary`、`notes`、`leave_time`。

品鉴师总结规则：

- 品鉴师只能给自己接待的旅行团填写 `taster_review_summary`。
- 没有产生有效订单的旅行团，品鉴师必须填写接待总结。
- 已经产生有效订单的旅行团，品鉴师可以选择性填写接待总结。
- 有效订单建议指 `order_status` 为 `valid` 或 `partial_refund` 的订单；`refunded` 和 `cancelled` 不算有效出单。
- “是否出单”由后端根据该旅行团是否有关联有效订单计算，不让品鉴师手工选择，避免误填。

为什么增加 `finance_mark`：

旅行团刚录入时默认未确认，标记为 0。财务核对后改为 1。老板或前台开启全局标记查询后，普通查询只展示标记为 1 的旅行团。

当前标记状态只以 `finance_mark` 判断；`marked_by` 和 `marked_at` 只表示最后一次标记操作的审计信息。

## 4.1 旅行团损耗表 `travel_group_losses`

用途：

记录每个旅行团在接待、品鉴过程中产生的酒水损耗。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| travel_group_id | uuid | 对应旅行团 |
| product_name | text | 损耗品名 |
| quantity | integer | 损耗数量 |
| notes | text | 备注，可为空 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

为什么单独建表：

一个旅行团可能产生多种酒品损耗。如果把损耗写在旅行团备注里，后面很难统计某个酒品一共损耗多少。单独建表后，一个旅行团可以有多条损耗记录，财务、库管和老板以后都可以按旅行团、品名、时间范围查询损耗情况。

第一版规则：

- 每条记录只记录一个品名和一个数量。
- 数量先用整数记录，适合按瓶、盒、件等方式统计。
- 如果后面需要记录半瓶、毫升、克数，再增加单位或小数字段，不在第一版复杂化。

## 5. 客户表 `customers`

用途：

保存购买客户基础信息。

主要字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | uuid | 主键 |
| name | text | 姓名 |

当前标记状态只以 `finance_mark` 判断；`marked_by` 和 `marked_at` 只表示最后一次标记操作的审计信息。

| monthly_rebate_rate | numeric | 月返积分比例，可为空 |
| total_rebate_rate | numeric | 合计比例，可为空 |
| is_active | boolean | 是否启用 |
| effective_from | date | 生效开始日期 |
| effective_to | date | 生效结束日期，可为空 |
| created_at | timestamp | 创建时间 |
| updated_at | timestamp | 更新时间 |

旅行社积分计算：

- 旅行社扣酒成本 = 按旅行社和酒品匹配 `agency_deduction_rules` 后汇总。
- 旅行社上单金额 = 销售额 - 旅行社扣酒成本。
- 日返金额 = 旅行社上单金额 * 日返积分比例。
- 月返金额 = 旅行社上单金额 * 月返积分比例。

## 19. 全局标记查询规则

当 `system_settings.only_show_marked_records = true` 时：

- 已落库的旅行团类查询只返回对应表 `finance_mark = 1` 的记录，包括 `travel_groups`、`guide_carried_groups`、`pending_travel_groups`。
- 订单查询以 `sales_orders.finance_mark = 1` 表示该订单及订单内客户快照已经确认；关联客户或旅行团的标记不参与订单可见性判断。
- 客户查询只判断 `customers.finance_mark = 1`，旅行团查询只判断 `travel_groups.finance_mark = 1`，三类数据的全局标记口径彼此独立。
- 品鉴师统计、老板看板、财务导出、AI 查询都应使用同样过滤规则；当前已实现的业务列表、详情和财务概览由后端业务查询层统一处理。
- 管理员恢复开关后，系统按角色权限正常查询。

为什么这样设计：

全局标记按钮影响的是全公司查询口径，所以必须在数据库查询层统一处理，不能每个页面各写一套判断。

## 20. 统计口径

### 出单销售额

有效订单金额合计。

建议包含：

- `order_status = valid`
- `order_status = partial_refund` 时按扣除退款后的金额计算

### 退单销售额

售后单中已完成退款或退单的金额合计。

### 总销售额

出单销售额 - 退单销售额。

### 总接待团数

指定时间范围内的旅行团数量。

### 总接待人数

指定时间范围内旅行团人数合计。

### 团均销售额

总销售额 / 总接待团数。

### 人均销售额

总销售额 / 总接待人数。

### 打蛋率

没有产生有效订单的旅行团数量 / 总接待旅行团数量。

为什么统计口径要写在数据库设计里：

后端开发、财务验收、老板看报表都要按同一套口径，否则每个人看到的数据会不一样。
