# 第 5 阶段二维码销售单和导出差距清单

生成日期：2026-07-01

本清单根据 `docs/20_第5阶段二维码销售单和导出开发文档.md`，并参考 `docs/06_开发阶段计划.md`、`docs/05_数据库初步设计.md`、`docs/17_第4阶段客户和销售订单开发文档.md`、`docs/18_第4阶段逐次开发提示词.md` 和 `docs/19_第4阶段云服务器测试验收清单.md`，对照当前代码生成。

本次只做文档检查，不修改 `schema.prisma`，不安装依赖，不写业务代码，不连接生产库。

## 1. 检查结论速览

- 第 4 阶段客户、销售订单、旅行团关联、列表筛选、角色数据范围和全局标记过滤的主要代码已经存在，可作为第 5 阶段复用基础。
- `SalesOrder` 仍缺少第 5 阶段二维码字段：`qrCodeToken`、`qrCodeGeneratedAt`、`qrCodeExpiresAt`。
- 后端已有通用 `SalesOrder` DTO，但没有面向销售单/公开扫码页的安全 DTO；没有二维码生成接口、认证销售单预览接口、公开扫码 HTML 页或 Excel 导出接口。
- 后端依赖中没有 `exceljs` 或等价 xlsx 生成库。
- Flutter `pubspec.yaml` 没有 `qr_flutter`、`path_provider` 或等价直接依赖。
- Flutter `ApiClient` 只支持 JSON 请求，缺少二进制下载能力。
- `qr_sales_sheet_page.dart` 仍是静态假数据和二维码占位，没有接入真实订单、销售单预览、生成二维码或复制链接。
- 订单详情页缺少“二维码销售单”入口；订单列表缺少销售订单 Excel 导出入口；旅行团查询页缺少旅行团 Excel 导出入口。
- 后端和 Flutter 测试均未覆盖二维码 token、公开页、Excel 导出、二进制下载、导出权限和导出全局标记过滤。

## 3. 缺失字段

`server/api/prisma/schema.prisma` 的 `SalesOrder` 当前没有以下第 5 阶段二维码字段：

```prisma
qrCodeToken       String?   @unique @map("qr_code_token") @db.VarChar(80)
qrCodeGeneratedAt DateTime? @map("qr_code_generated_at") @db.DateTime(0)
qrCodeExpiresAt  DateTime? @map("qr_code_expires_at") @db.DateTime(0)
```

也缺少建议索引：

```prisma
@@index([qrCodeExpiresAt])
```

说明：
- 本次未修改 schema。
- 后续 migration 需要保证旧订单字段为空可用，`qrCodeToken` 唯一但允许多条 `NULL`。
- 需要同步更新 Prisma schema smoke 测试和 migration 清单。

## 4. 缺失接口

### 4.1 销售单 DTO

当前已有 `toSalesOrderDto(order)`，但它是内部订单 DTO，会返回 `financeMark`、`markedById`、`financeRemark`、`warehouseRemark`、`salesUserId` 等内部字段。

第 5 阶段缺少单独的 `SalesSheet` DTO/builder：
- 认证预览页可包含二维码状态。
- 公开扫码页只能返回/渲染客户可见字段。
- 客户电话需要脱敏。
- 公开页不能泄露财务备注、库管备注、内部标记、操作日志、内部用户 ID。

### 4.2 二维码接口

缺少：
- `GET /api/sales-orders/:id/sales-sheet`
- `POST /api/sales-orders/:id/qr-code`

后续实现需要：
- 生成不可猜 token。
- `regenerate=false` 时复用未过期 token。
- `regenerate=true` 时替换 token，并写 `operation_logs`。
- 鉴权查询复用 `getSalesOrder` 的读取范围和全局标记过滤。

### 4.3 公开扫码页

缺少：
- `GET /api/public/sales-sheets/:token`

后续实现需要：
- 新增 public controller 或等价路由。
- 使用 `@Res()` 直接返回 HTML，绕开全局 `ApiResponseInterceptor` 的 JSON 包装。
- 对所有动态文本做 HTML escape。
- token 不存在或过期时返回友好 HTML，避免泄露订单存在性和内部信息。

### 4.4 Excel 导出接口

缺少：
- `GET /api/sales-orders/export.xlsx`
- `GET /api/travel-groups/export.xlsx`

注意路由顺序风险：
- 当前 `sales-orders.nest.controller.ts` 中 `@Get(':id')` 已存在。后续 `@Get('export.xlsx')` 必须放在 `@Get(':id')` 前面。
- 当前 `travel-groups.nest.controller.ts` 中 `@Get(':id')` 已存在。后续 `@Get('export.xlsx')` 也必须放在 `@Get(':id')` 前面。

## 7. 导出接口复用方案

### 7.1 销售订单导出

建议不要另写一套 where 逻辑。应在 `BusinessDataNestService` 内抽出可复用查询：

- 继续使用 `buildSalesOrderWhere(filters)` 处理列表筛选：
  - `dateFrom`
  - `dateTo`
  - `query` / `keyword`
  - `customerId`
  - `customerPhone`
  - `travelGroupId`
  - `orderType`
  - `status`
  - `deliveryType`
  - `packingStatus`
  - `financeMark`
  - `customerFinanceMark`
  - `salesUserId`
- 继续使用 `buildScopedSalesOrderWhere(actor, baseWhere)` 叠加：
  - 角色数据范围。
  - 全局 `only_show_marked_records` 过滤。
- 导出接口本身只允许 `admin`、`finance`。
- 查询 include 应至少包含 `items`、`customer`、`travelGroup`，如要显示销售人员姓名，还需要补 `salesUser` include 或在 DTO 中补销售人员名称。
- 当前 `normalizeTake` 最大 200，不适合 Excel 导出。导出应单独使用最大行数限制，例如 5000，超过则返回明确错误，避免改变现有列表分页口径。

### 7.2 旅行团导出

建议复用旅行团列表口径：

- 继续使用 `buildGroupWhere(filters, 'travel')` 处理筛选：
  - `dateFrom`
  - `dateTo`
  - `keyword`
  - `groupNo`
  - `guideId`
  - `tasterId`
  - `groupType`
  - `financeMark`
  - `pendingStatus`
- 继续使用 `buildRoleScopedTravelGroupWhere(actor, baseWhere)` 叠加：
  - 角色数据范围。
  - 全局 `only_show_marked_records` 过滤。
- 导出接口本身只允许 `admin`、`finance`。
- `pendingStatus` 是计算字段，当前列表会先查数据再通过 `filterGroupDtosByComputedFields` 过滤；导出也要复用同一计算过滤，避免页面和 Excel 不一致。
- 导出字段如需“是否出单”“订单总额”，应复用 `toGroupDto` / `buildTravelGroupOrderSummaryDto` 的有效订单口径，而不是重新计算一套。
- 同样需要独立最大行数限制，避免受列表默认 `limit=50` 和最大 200 影响。

### 7.3 全局标记过滤

当前全局过滤口径已经集中在 service：
- 销售订单：客户必须已标记；若关联旅行团，旅行团也必须已标记。
- 旅行团：旅行团必须已标记。

导出接口应调用同一 service 查询方法或同一 scoped where builder，不能只在 Flutter 端隐藏数据，也不能绕过 `buildGlobalSalesOrderMarkScope()` / `buildGlobalGroupMarkScope()`。

## 9. 风险

- 远端第 4 阶段 smoke 仍有阻塞记录：`docs/19_第4阶段云服务器测试验收清单.md` 记录 API 502、SSH 超时、测试库未重新确认。第 5 阶段如涉及云服务器，必须先确认远端数据库是测试库，未确认前只做只读检查。
- 当前工作区已有多处未提交改动，包括 Flutter、后端、docs 和 `server/api/package.json`。后续实现前应先确认这些改动的归属，避免覆盖用户改动。
- `SalesOrder` 缺二维码字段，后续必须先做 schema/migration，否则二维码接口无法落库。
- `qrCodeToken @unique` 在 MySQL 中多条 `NULL` 可共存，但 migration 仍需在测试库验证。
- 公开 HTML 页如果未统一 escape，会有 XSS 风险。
- 公开页若复用内部 `toSalesOrderDto`，会泄露财务/库管/标记/内部 ID 字段。
- 导出如绕过现有 scoped where，会导致 Excel 和页面数据不一致，尤其是全局标记过滤开启时。
- `GET /export.xlsx` 路由顺序如果放在 `@Get(':id')` 后面，可能被误认为详情 id。
- `ApiResponseInterceptor` 会包装普通返回值，导出文件和公开 HTML 必须用 `@Res()` 或等价方式直接发送响应。
- `pubspec.lock` 中传递依赖不能替代 `pubspec.yaml` 的直接依赖声明，后续需要明确安装。
