# 第 11 阶段：多仓库存管理开发文档

更新日期：2026-08-01

## 0. 2026-08-01 独立仓库管理页面实施结果

本轮在不复制库存记账、调拨、盘点、逐瓶和销售履约状态的前提下，完成仓库档案与仓库商品维护的独立入口：

- 保留 `warehouse_management` destination ID，显示名改为“库存管理”，继续承载入库、调拨、盘点、流水、预警和报表等综合工作台。
- 新增 `warehouse_directory` destination，显示名为“仓库管理”；桌面使用两级仓库树加右侧详情，手机使用仓库卡片与独立详情。
- 原库存工作台不再提供可写“仓库设置”，避免两套仓库档案写入口；逐瓶兼容入口仍复用原页面。
- `Warehouse.parentWarehouseId` 为可空自关联。服务端和数据库触发器共同限制最多两级，禁止自关联、循环、已有子仓的仓库变成子仓；默认仓和销售履约仓必须是启用父仓。
- 新增 `WarehouseProductConfiguration`。关联表不保存实际数量；实际数量继续来自余额快照及其不可变流水、批次和逐瓶事实。
- 父仓商品查询同时返回 `localStock` 与 `inclusiveStock`。汇总在服务端对父仓及全部直属子仓做全量数据库聚合，只用于读取，不写回父仓余额，也不参与订单占用或出库；逐瓶商品的现存、占用和不可售数量按真实逐瓶状态聚合，在途数量继续使用与逐瓶调拨交叉校验的库存投影。
- 普通商品的非零初始数量调用现有 `OPENING` 命令，在仓库商品关联事务内生成正式单据、批次、流水和余额快照；已有历史时拒绝再次开账。逐瓶商品只能先以零库存添加，再进入现有逐瓶页面录入真实物流码。
- 仓库商品移除实际为安全停用；库存、占用、不可售、在途或有效逐瓶记录非零时拒绝。再次添加优先恢复原关联。
- 仓库物理删除仅允许无子仓、非默认且从未产生仓库商品关联、库存或业务历史的空仓；失败返回稳定错误码和完整中文原因，引导停用。

历史仓库商品关联不在 migration 中静默回填。部署后先运行 `npm run backfill:warehouse-products` 预览，再经人工确认使用 `npm run backfill:warehouse-products -- --apply`；脚本按仓库与商品唯一键重复执行安全。

技术实现和迁移边界以 `docs/46_第11阶段多仓库存管理Schema差距清单.md` 为准。本文定义业务与总体架构口径；两份文档有冲突时，必须先按当前代码重新复核并更新文档，不能直接猜测实现。

## 1. 阶段目标

在现有商品、销售订单、售后、库管打包和茅台逐瓶库存基础上，新增统一的多仓库存系统。所有酒类商品均纳入库存管理，计量单位统一为“瓶”。

本阶段采用“通用数量库存账 + 茅台逐瓶明细”的双层模型：

- 普通酒按仓库、商品和批次数量管理。
- 茅台继续逐瓶保存物流码、生产日期、生产批次、批次序号和逐瓶进货价，同时按仓库汇总数量。
- 库存余额是查询快照，库存流水是不可变事实。任何业务不得直接修改余额绕过流水。

## 2. 已确认业务口径

- 库存覆盖商品库中的全部酒类商品。
- 库存单位只使用“瓶”，本阶段不做箱、件、瓶换算。
- 支持多个仓库。
- 茅台继续逐瓶管理，并自动汇总库存数量。
- 展示账面现存、已占用、实际可售、不可售和短缺数量。
- 邮寄订单保存时占用库存，库管确认“已打包”时正式出库。
- 自带商品保存订单时立即出库。
- 库存不足不阻止销售保存订单，普通数量库存允许出现负数并触发预警。
- 茅台不得伪造物流码；不足部分保存为“缺货待配瓶”。
- 取消未出库邮寄订单时自动释放占用。
- 已出库订单只有在库管确认实际收到退货后才能返还库存；退款或售后完成本身不能增加库存。
- 入库类型包括采购入库、顾客退货、盘盈、其他入库、调拨入库和期初库存。
- 采购入库记录供应商、采购单号、生产批次、生产日期和进货价。
- 初始库存按仓库、商品逐项手工录入。
- 库管负责出入库、调拨和盘点；财务维护和查看成本；销售不可查看任何库存数量；老板和管理员查看全部。
- 普通入库、出库和调拨不审批。
- 盘点按仓库、单个商品发起，差异必须填写原因并由老板或管理员审批后生效。
- 每个仓库、商品可以配置最低库存；只做系统内预警和待办，不发短信或微信。
- 第一版提供库存余额、出入库流水、销售出库、采购入库、批次余额、库存预警、盘点差异、调拨和库存金额报表及 Excel 导出。

## 3. 商品库存模式

`Product.inventoryTrackingMode` 扩展为：

- `NONE`：不管理库存，保留给未来非实物商品。
- `QUANTITY`：普通酒，按瓶管理数量。
- `SERIALIZED`：茅台，逐瓶管理。

迁移不得在生产库中直接把全部商品静默改为 `QUANTITY`。应提供可预览、可重复执行的切换脚本，由管理员在库存启用前确认目标商品。

库存模式必须按受控状态机切换：

- 当前通用商品新增/编辑接口不得继续承担库存模式切换。模式变更使用专用命令，至少接收 `expectedCurrentMode`、目标模式、启用时间、幂等键和请求内容 hash。
- `NONE -> QUANTITY` 只有在目标仓库、开账方案和启用边界均已准备后才能生效；开账必须生成正式期初单据和流水，不能直接写余额。
- 商品产生有效库存流水后不得直接切回 `NONE`。
- `QUANTITY <-> SERIALIZED` 不允许在线直接互转，必须走专项 dry-run、冲突处理和人工确认。
- 有库存事实后不得直接修改 `Product.unit`；本阶段统一为整数瓶，不支持通过改单位重写历史数量。

Prisma/MySQL 枚举采用 expand/contract：先只增加 `QUANTITY` 并保持旧值兼容；一旦已有商品写入新值，旧应用只能回滚到仍能识别数据库超集的版本，不得直接缩回枚举。

## 4. 多仓规则

仓库主数据至少包含编号、名称、地址、负责人、是否启用和是否默认仓库。全系统只能有一个启用的默认仓库。

唯一默认仓必须有数据库可验证的保证。优先使用可空唯一 `activeDefaultKey`（只有启用默认仓写固定值）并配合一致性 CHECK；如果目标 MySQL 版本不适用，则使用单行库存配置表的 `defaultWarehouseId` 外键和事务锁。不得只靠 Flutter 或先清空再设置的非事务逻辑。

第一版采用“一张订单对应一个履约仓库”：

- 销售保存订单时由服务端自动使用默认仓库，销售端不返回仓库余量。
- 库管可以在正式出库前更换履约仓库。
- 更换仓库必须在同一事务内释放原仓占用并在新仓重新占用。
- 已发生销售出库后不得直接更换仓库。
- 第一版不支持一张订单拆分多个仓库发货；需要跨仓供货时先调拨。

调拨采用两步确认：

1. 调出后从来源仓减少，数量进入调拨在途。
2. 调入仓确认收到后计入目标仓。

调入确认属于实物收货确认，不属于审批。取消或纠错必须通过反向单据和原因完成。

调拨在途必须有明确的存储或可重建口径。余额快照可保存 `inTransitQty`，也可由调拨流水/收货行重建，但页面、API、报表和公司总量必须使用同一口径。

## 5. 数量定义

每个“仓库 + 商品”维护以下查询快照：

- `onHandQty`：账面现存。
- `reservedQty`：有效邮寄订单尚未出库的占用。
- `unavailableQty`：残损、冻结、待补成本等不可售数量。
- `inTransitQty`：已从来源仓调出、尚未被目标仓确认收到的数量。
- `availableQty = onHandQty - reservedQty - unavailableQty`。
- `shortageQty = max(0, -availableQty)`。

账面现存计算：

```text
期初库存
+ 采购入库
+ 顾客退货
+ 盘盈
+ 其他入库
+ 调拨入库
- 销售出库
- 盘亏
- 其他出库
- 调拨出库
= 账面现存
```

普通商品允许 `onHandQty` 或 `availableQty` 为负，但每次产生负数都必须生成系统内预警。`reservedQty`、`unavailableQty` 和 `inTransitQty` 不得为负。

库存余额可以做性能快照，但必须能从库存流水重建和校验。外部服务不能直接更新库存余额。

## 6. 单据、流水和幂等

建议建立以下库存事实：

- 库存单据及单据明细。
- 不可修改的库存流水。
- 订单占用记录。
- 商品批次及批次剩余数量。
- 仓库商品余额快照。
- 库存命令幂等回执。
- 调拨单、调拨明细和分次收货记录。
- 最低库存配置。

所有自动库存事件必须具有规范化的非空稳定来源键，例如：

```text
sourceType + sourceId + sourceLineId + eventType
```

数据库以单一非空 `sourceKey` 建立唯一约束，保证接口重试、重复点击或并发请求不会重复占用、重复出库或重复返库。不得只依赖包含可空批次、逐瓶或来源行字段的复合唯一键，因为 MySQL 允许多条含 NULL 的“重复”唯一键。

每个写命令还必须保存 `idempotencyKey`、`requestHash`、命令类型和结果单据，例如使用 `InventoryCommandReceipt`：

- 相同 key 和相同 hash 返回第一次成功结果。
- 相同 key 但不同 hash 返回稳定冲突错误。
- HTTP `requestId` 只用于追踪，不能代替业务幂等键。

事务内应依次抢占幂等键、条件更新/锁定余额与批次、写单据和流水、更新快照、写角色安全日志。Todo 和读模型刷新采用提交后事件或可补偿机制，失败时不能重放库存事实。

已生效流水禁止物理删除和原地改数量。纠错必须生成冲销流水和新的正确流水，并记录原因、操作者及 before/after。

库存事实之间的外键原则上使用 `Restrict`，人员审计外键使用 `SetNull` 并保留操作者快照。冲销来源使用一对一唯一关系，防止同一流水或单据被重复冲销。

## 7. 批次和成本

普通商品采购批次记录：

- 仓库、商品。
- 供应商、采购单号。
- 生产批次、生产日期。
- 入库数量、剩余数量。
- 进货单价和总金额，金额使用整数分。
- 成本状态、经办人和审计时间。

库管录入非成本字段；财务或管理员维护进货价。库管接口、页面、导出和操作日志 DTO 不得泄露成本。

普通商品出库优先按先进先出分配有剩余数量的批次。库存为负或正批次不足时，超出部分可以生成无批次、无成本覆盖的出库流水，不得伪造批次或成本；财务报表必须显示成本覆盖状态。

本阶段的采购批次成本用于库存金额和批次追踪，不替换现有 `ProductActualCost` 与销售订单毛利快照口径，不追溯改写历史订单毛利。

## 8. 销售订单联动

| 业务事件 | 库存行为 |
| --- | --- |
| 保存邮寄明细 | 增加订单占用，不减少账面现存 |
| 修改未出库邮寄明细 | 按商品和数量差额调整占用 |
| 库管确认已打包 | 释放对应占用并生成销售出库 |
| 保存自带明细 | 立即生成销售出库 |
| 取消未出库邮寄订单 | 自动释放占用 |
| 取消或退款已出库订单 | 不自动增加库存 |
| 库管确认实际收到退货 | 自动生成顾客退货入库 |
| 售后补发、换货 | 形成新的占用和销售出库 |

一张订单可以同时含自带和邮寄明细，库存处理按明细的 `deliveryType` 分开执行。

未出库邮寄明细可以正常修改并按差额同步占用。已出库明细不得通过普通订单编辑改变商品或数量；需要走退货、补发、换货或带原因的库存纠错流程。

订单库存联动必须覆盖当前全部写路径，而不是只修改库管打包接口：

- 新建订单。
- 销售一次编辑 `sales-edit`。
- admin/finance 通用订单 PATCH。
- finance PATCH 中的状态变更。
- 独立 status PATCH。
- sales-order packing PATCH。
- `warehouse/orders/:id/packing` 别名路径。

当前订单明细编辑会删除后重建记录，因此必须为库存明细增加服务端稳定的 `inventoryLineKey`，或把更新改为能保留稳定行键的差异 upsert。不得直接使用可能变化的 `SalesOrderItem.id` 作为占用和出库的唯一业务键。

订单至少增加可空 `fulfillmentWarehouseId`、`inventoryAppliedAt`、`inventoryPolicyVersion` 和库存版本字段。历史记录可为空，新库存订单由服务端填充。已出库后的商品/数量修改必须由后端拒绝。

售后流程当前会生成 `orderType=AFTER_SALES`、`packingStatus=PACKED`、明细 `SELF_PICKUP` 的财务负向销售订单。该记录不是实物销售出库，所有自动订单库存钩子和切换脚本必须明确排除，补发/换货则通过单独的履约命令触发。

库存启用时间之前的历史订单不生成库存流水。库存启用时仍有效且未打包的邮寄订单，可通过一次性切换脚本生成占用。

## 9. 茅台逐瓶库存

`SerializedInventoryUnit` 必须增加仓库归属，并能区分：

- 待补成本。
- 可售。
- 已占用。
- 已出库。
- 不可售。
- 作废。

状态迁移采用 expand/contract：第一批 migration 增加 `RESERVED/OUTBOUND/UNAVAILABLE`，但暂时保留现有 `ALLOCATED`；新代码停止写 `ALLOCATED`。只有 dry-run 将历史记录全部分类、冲突清零、观察窗口结束后，才允许另一个 migration 删除旧值。

逐瓶状态与通用库存流水必须一致：

- 待补成本计入账面现存和不可售。
- 已占用计入账面现存和订单占用。
- 已出库不再计入账面现存。
- 不可售计入账面现存和不可售。

销售角色不再读取可售逐瓶清单。销售只提交商品和数量：

- 邮寄订单由库管打包时选择具体物流码。
- 自带订单由服务端按稳定的先进先出规则自动匹配可售瓶码。
- 可售瓶码不足时订单仍保存，差额进入缺货待配瓶，不创建虚假瓶码。

茅台调拨必须逐瓶选择物流码。顾客退货优先关联原销售瓶码；无法确认物流码时不能直接恢复原瓶状态。

建议使用 `SerializedInventoryAssignment` 保存逐瓶占用、出库和释放历史，单瓶表上的旧订单外键只作为兼容快照。有效占用使用非空唯一活动键，逐瓶的仓库、状态和版本采用条件更新。单瓶状态、Assignment、库存流水和仓库商品余额必须能四方交叉校验。

历史 `ALLOCATED` 不能只根据现有字段直接转换：

- 有效且未打包的 shipping 订单只能列为候选占用。
- shipping + PACKED 只能列为候选出库，因为旧打包路径不改变逐瓶状态。
- self-pickup 的历史 `PACKED` 是默认值，不能据此推断真实出库。
- CANCELLED/REFUNDED 仍为 `ALLOCATED` 的记录不得自动释放或出库。
- 缺订单、缺明细、混合配送或资料不完整者进入冲突报告，不进入新可售池。

逐瓶并发分配必须在真实 MySQL 或隔离库中验证，不能只依赖内存 mock 的 `updateMany` 测试。

## 10. 售后退货

现有系统已经有逐商品 `AfterSalesOrderItem`，但它表示售后/退款计算明细，不是仓库收货事实。应保留该模型兼容历史，并增加 `returnRequired`、`expectedReturnQty`；历史记录默认不要求退货，不得从退款数量猜造。

实际收货使用独立、可分次的事实模型：

- `AfterSalesReceipt`：售后单、实际收货仓、状态、幂等键、请求 hash、确认/冲销审计。
- `AfterSalesReceiptLine`：关联售后商品明细、实际收到数量、可售/不可售/异常状态、普通批次和备注。
- `AfterSalesReceiptSerializedUnit`：扫描物流码、匹配到的原逐瓶记录和异常状态。

同一售后可多次、不同批次收货；每次收货独立幂等，累计实际收到数量不得超过应退数量，并发确认不能超收。旧 `warehouseConfirmedAt/By/Note` 只保留历史展示，不能推断实际收到数量、收货仓或返库。

财务确认退款、订单状态变为退款或售后单完成，都不能直接增加库存。只有库管确认实际收到商品后，服务端才自动生成幂等的退货入库单和库存流水。

## 11. 盘点

盘点按“仓库 + 单个商品”发起：

1. 保存发起时的账面数量快照。
2. 库管填写实盘数量、不可售数量和差异原因。
3. 提交后等待老板或管理员审批。
4. 审批通过后生成盘盈或盘亏流水。
5. 驳回后退回修改。

审批前不得改变库存。提交人不能通过修改原单绕过审批。审批、驳回和生效都写入操作日志。

同一“仓库 + 商品”只允许一个活动盘点，可使用可空唯一 `activeKey` 保证。提交时保存余额版本和最后流水 ID；批准前若期间发生任何库存流水，必须拒绝旧差异并要求重新盘点。逐瓶盘点另存扫描结果，不能只改汇总数量。

## 12. 角色权限

| 角色 | 数量 | 成本 | 库存写操作 | 盘点审批 |
| --- | --- | --- | --- | --- |
| warehouse | 可见 | 不可见 | 入库、出库、调拨、退货、盘点 | 否 |
| finance | 可见 | 可见并可维护采购成本 | 不可直接调整数量 | 否 |
| sales | 不可见 | 不可见 | 无 | 否 |
| boss | 全部可见 | 可见库存采购成本和库存金额 | 原则上只读 | 是 |
| admin/super_admin | 全部可见 | 全部可见 | 全部管理能力 | 是 |

老板在本阶段可查看库存采购成本，但不得顺便放宽现有商品实际成本、扣单成本、提成成本等非库存接口，除非另有明确需求。

售后角色只查看与售后单相关的退货进度，不查看全仓库存数量和成本。

权限必须在后端执行。销售库存接口应返回 403 或等价无权结果，不能只隐藏 Flutter 菜单。公开二维码销售单、普通订单 DTO、导出、AI 助手和操作日志均不得向无权角色泄露库存、仓库成本或内部瓶码状态。

当前订单和售后内部 DTO 会向多个可读角色返回逐瓶 ID、物流码和生产资料；第 11 阶段必须改为按 actor 显式投影，不能只删除销售端 picker。OperationLog 的通用 sanitizer 不会自动识别采购成本、库存数量或瓶码，新日志、错误详情和 Excel 必须从源头使用字段白名单。公开二维码继续保持显式安全 DTO。

## 13. 预警和报表

最低库存按“仓库 + 商品”配置。以下情况生成系统内预警和待办：

- 可售数量低于或等于最低库存。
- 可售数量为负。
- 茅台或普通批次待补成本。
- 有订单缺货待配。
- 调拨长时间未收货。
- 盘点等待审批。

不发送短信或微信。

库存预警通过稳定 `InventoryAlert` 来源接入现有 TodoReminder，可扩展 `INVENTORY_ALERT/STOCKTAKE` 来源类型。销售永不成为库存预警收件人，Todo 的标题、内容和 sourceSnapshot 不得包含全仓数量、采购成本或瓶码。

现有 Todo 定时补偿扫描有固定 200 条窗口；接入库存后必须使用事件触发 + 游标/分页补偿，避免大量预警时旧记录长期饥饿，并测试超过 200 条、重复调度、恢复和再次触发。

第一版报表：

- 各仓库存余额和全公司汇总。
- 指定期间期初、入库、出库和期末。
- 出入库流水。
- 销售出库。
- 采购入库。
- 批次剩余库存和成本覆盖。
- 库存预警。
- 盘点差异。
- 调拨记录。
- 财务库存金额。

报表支持页面查询和 Excel 导出，导出权限与页面字段权限完全一致。

库存余额和订单自动处理不受全局“只查询已标记信息”开关影响；现有订单查询页面是否隐藏未标记订单继续沿用原规则。AI 助手第一版不增加库存查询能力。

## 15. 上线切换

上线前必须设置库存启用时间，并完成：

- 创建仓库和唯一默认仓库。
- 将目标酒类商品切换为 `QUANTITY`，茅台保持 `SERIALIZED`。
- 逐仓、逐商品手工录入期初数量。
- 给现有茅台逐瓶数据分配仓库。
- 对库存启用时仍有效且未打包的邮寄订单生成一次性占用。
- 将启用前已打包订单视为历史已出库，不再次扣减。

上线配置包括生产仓库名称/code/地址/负责人、唯一默认仓、各仓商品阈值、调拨逾期时长、预警 SLA、`goLiveAt` 和维护窗口。这些值未确认不得阻止本地 Schema、领域服务、测试 fixture 和 UI 架构开发；本地 fixture 不得写入生产 migration 或 seed。

切换至少包含以下默认只读能力：

- preflight：migration/MySQL 版本、商品模式和单位、订单状态组合、逐瓶状态/绑定/完整性。
- warehouse bootstrap：从参数/版本化配置预览建仓和唯一默认仓。
- product mode plan：只处理显式商品 ID 和 `expectedCurrentMode=NONE`。
- serialized warehouse plan：按状态和订单分类历史逐瓶；不确定数据只列冲突。
- opening import plan：只接受人工期初，不从历史销售反推。
- open orders cutover：仅处理启用时有效、未出库 shipping 明细，使用稳定库存行键，并排除 `orderType=AFTER_SALES`。
- open after-sales plan：旧仓库确认不推断实际收货。
- rebuild verify：流水、余额、批次和逐瓶交叉校验。
- rollback report：区分可撤销草稿和只能用冲销处理的已生效事实。

所有切换脚本必须默认 dry-run；只有显式 `--apply`、目标环境确认、备份确认、维护写入冻结和输入 manifest hash 一致后才能写入。每一步输出 run ID、输入 hash、`planned/created/reused/skipped/conflict/warning` 和稳定记录标识，重复执行不重复写入，扫描与 apply 间数据变化视为并发冲突。

已生效库存流水不是可通过 down migration 删除的临时数据。切流后的回滚只能是关闭新入口并保留数据库超集、写补偿/冲销流水，或在维护窗口恢复整库备份。

未确认测试库和数据库备份前，不得在云端执行迁移、seed、切换或写入 smoke。

## 16. 核心验收原则

- 任意仓库商品余额可由库存流水重建，重建值与快照一致。
- 接口重试和并发操作不会重复占用、重复出库或重复返库；同幂等键不同请求内容会稳定拒绝。
- 邮寄、自带、取消、订单修改、已打包、退货、调拨和盘点口径正确。
- 新建、sales-edit、通用 PATCH、finance/status、两条 packing 路径均无法绕过库存领域服务。
- 售后生成的财务负向销售订单不会触发库存出库。
- 普通商品可负库存并产生预警；茅台不足不创建虚假物流码。
- 退款不返库存，实际收货确认才返库存。
- 历史 `ALLOCATED`、自提默认 `PACKED` 和旧售后仓库确认均不会被脚本猜成物理事实。
- 销售无法通过菜单、接口、导出、日志或 AI 获得库存数量。
- 库管无法通过接口、导出、日志或错误响应获得采购成本。
- 老板只能查看本阶段库存采购成本，不扩大现有非库存成本权限。
- 历史订单、现有毛利、提成、积分、二维码销售单和物流流程不被追溯改写。
- migration 从上一阶段基线可全新部署，切换脚本第二次执行零重复；真实 MySQL 并发、余额重建和超过 200 条 Todo 补偿测试通过。
