# 订单部分金额走个人：迁移、校验与回滚

## 部署顺序

1. 先备份 `sales_orders`、`after_sales_orders`、`commission_records`、
   `travel_group_finance_summaries`、`guide_points_summaries` 和
   `operation_logs`。
2. 确认 `_prisma_migrations` 已完整应用到
   `20260729000300_travel_group_not_entered_confirmation`。尤其必须先应用
   `20260727000100_guide_personal_points`，否则数据库不存在
   `points_destination`，当前 Prisma Client 的订单查询会以 `P2022/P2010`
   失败；其中 `P2022` 会被安全映射为 HTTP 503、
   `DATABASE_SCHEMA_MISMATCH` 和错误编号。
3. 生产或已有数据环境确认备份可恢复后，设置
   `API_DATABASE_BACKUP_CONFIRMED=1`，从 `server/api` 执行
   `npm run deploy:pm2:safe`。该入口会依次完成 Prisma Client 生成、构建、
   `prisma migrate deploy`，全部成功后才启动或重启 PM2；不会执行 seed。
4. 重启后执行订单列表、订单详情和
   `PATCH /api/sales-orders/:id/points-destination` 冒烟验证。

如果任一历史 migration 在目标环境中曾部分失败，不要修改已经在其他
环境执行过的历史 `migration.sql`。先停写并确认备份与实际表结构，再创建
新的前向修复 migration，以可重复检查的方式补齐缺失字段、索引、约束及
回填；在修复 migration 和 Prisma migration 记录的处置方案完成评审前，
不要执行 `migrate resolve` 或重启新 API。

### 隔离空库演练阻断（2026-08-01）

在本地 MySQL 8.0.46 空库执行当前仓库的完整 `prisma migrate deploy`
时，迁移链在到达本功能迁移前，被历史迁移
`20260727000800_serialized_inventory_unification` 阻断：MySQL 不允许
`inventory_movements.reservation_id` 同时用于带 `SET NULL` 动作的外键和
`inventory_movements_nonzero_delta_check` 检查约束。该结果不证明生产库处于同一状态，但会阻止
当前迁移集建立新的全量环境。发布前必须先取得生产/测试环境的只读
`migrate status`、`_prisma_migrations` 和实际列排序规则；不得为了让空库
通过而改写已发布的历史 migration，也不得在未评审的情况下执行
`migrate resolve`。新环境需要采用经评审的新基线；已部分失败的既有环境
需要在备份后按实际对象状态完成前向修复。

同日使用当前 `schema.prisma` 建立一次性 MySQL 8.0.46 隔离库的功能验证
已通过：全部走个人、部分金额、修改收款导游与返点、取消走个人、售后退款
拆分，以及下游导游汇总失败时订单/普通汇总/导游汇总/提成/日志整体回滚。
这只能证明当前 schema 上的业务与事务行为，不能替代上述完整 migration
链演练。

## 回填规则

- 历史 `points_destination = 'guide_personal'` 的订单：
  `personal_amount_cents = total_amount_cents`。
- 其他历史订单：`personal_amount_cents = 0`。
- 历史整单走个人订单关联的售后退款：
  `personal_points_refund_amount_cents = refund_amount_cents`，保留旧版
  导游积分退款口径；其他历史售后单回填 0。

## 约束与索引

- `personal_amount_cents` 必须位于 `0..total_amount_cents`。
- `personal_amount_cents = 0` 时兼容字段必须为 `travel_agency`；大于 0
  时必须为 `guide_personal`。
- `personal_points_refund_amount_cents` 必须位于
  `0..refund_amount_cents`。
- 新增个人金额、团号+个人金额、订单+确认状态+个人退款金额索引，分别
  支持导游积分刷新、普通积分刷新和已确认退款汇总。

## 回滚

回滚会丢失部分金额和退款归属信息，必须先停写并保留备份。若业务要求
继续兼容旧版整单模型，应先把所有部分订单归并为整单状态：

```sql
UPDATE sales_orders
SET points_destination =
  CASE WHEN personal_amount_cents > 0
       THEN 'guide_personal'
       ELSE 'travel_agency'
  END;
```

然后按以下顺序删除约束、索引和列：

```sql
ALTER TABLE after_sales_orders
  DROP CHECK after_sales_orders_personal_refund_bounds_chk,
  DROP INDEX after_sales_orders_personal_refund_idx,
  DROP COLUMN personal_points_refund_amount_cents;

ALTER TABLE sales_orders
  DROP CHECK sales_orders_points_destination_amount_chk,
  DROP CHECK sales_orders_personal_amount_bounds_chk,
  DROP INDEX sales_orders_travel_group_personal_amount_idx,
  DROP INDEX sales_orders_personal_amount_cents_idx,
  DROP COLUMN personal_amount_cents;
```

MySQL 版本若不支持 `DROP CHECK`，应使用该版本对应的
`DROP CONSTRAINT` 语法。回滚后重新生成 Prisma Client 并恢复旧版 API。
