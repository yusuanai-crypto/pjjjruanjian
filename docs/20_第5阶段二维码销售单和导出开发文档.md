# 第 5 阶段二维码销售单和导出开发文档

> 安全更新：公开销售单二维码是短期 Bearer capability。生成接口要求显式配置
> `PUBLIC_SALES_SHEET_BASE_URL` 为公网 HTTPS 地址，默认有效期 30 天、最长
> 90 天；服务端不再从 `Host` 或 `X-Forwarded-Host` 推导链接。已存在的二维码
> 需要显式使用 `regenerate=true` 轮换，也可通过
> `DELETE /api/sales-orders/:id/qr-code` 立即吊销。按当前业务确认，公开页面
> 返回订单客户快照中的完整电话、由省/市/区/详细地址拼接的完整收货地址，
> 以及配送、快递单号和标准化物流跟踪信息；除此之外仍按最小化原则，不公开
> 金额、旅行团、销售人员、开票、财务/库管备注、财务标记或数据库 ID。公开
> HTML 成功与失效响应均设置 `Cache-Control:
> no-store, private`、`Pragma: no-cache`、`Referrer-Policy: no-referrer`、
> `X-Content-Type-Options: nosniff` 和禁止 framing/外部资源的 CSP；无效、
> 过期和已吊销 token 返回同一 404 页面，并设置 `X-Robots-Tag:
> noindex, nofollow, noarchive` 与 robots meta。

版本：v0.1
状态：根据 `docs/06_开发阶段计划.md` 第 5 阶段目标整理。进入开发前先确认第 4 阶段客户、订单、旅行团关联、本地测试和测试库 smoke 已稳定。

## 1. 阶段目标

第 5 阶段目标是把“二维码销售单”和“Excel 导出”做成真实可用闭环：

- 销售可以从订单详情或二维码销售单页面生成二维码。
- 二维码指向该订单的公开销售单详情页，客人手机扫码即可查看。
- 客人可以对手机页面或销售手机/电脑上的二维码销售单拍照留存。
- 财务和管理员可以按当前筛选条件导出销售订单 Excel。
- 财务和管理员可以按当前筛选条件导出旅行团 Excel。
- 导出字段和页面显示口径一致，并遵守角色权限和全局“只查询已标记信息”开关。

本阶段完成后，里程碑 2“能录订单和生成二维码”才算真正闭环。

## 2. 本阶段不做的事

- 不做打印销售单。
- 不做完整售后单流程。
- 不做提成、积分、扣酒成本计算或提成导出。
- 不做 AI 查询。
- 不做复杂文件管理中心。
- 不把二维码公开页做成需要客户登录的系统。
- 不连接生产库，不覆盖生产数据。

## 4. 业务规则

### 4.1 二维码销售单规则

- 二维码内容是公开销售单 URL，不直接把订单内容编码进二维码。
- 默认 URL：`{PUBLIC_SALES_SHEET_BASE_URL}/api/public/sales-sheets/{token}`。
- `PUBLIC_SALES_SHEET_BASE_URL` 必须显式配置为公网 HTTPS 域名；禁止从请求
  `Host`、`X-Forwarded-Host` 或其他客户端可控请求头推导。
- token 必须随机、不可猜，建议使用 Node `crypto.randomBytes(24).toString('base64url')` 或等价方案。
- 所有 token 都必须过期：缺省有效期 30 天，可配置范围为 1 到 90 天。
- 已存在有效 token 时不得再次返回 bearer 值；用户必须显式重新生成或先吊销。
- 数据库只保存 token 的 SHA-256 查询哈希，操作日志只保存短指纹。
- 吊销或重新生成后，旧 token 立即失效。
- token 无效、过期、吊销或订单不存在时返回同一个 404 页面，不展示差异或订单内容。

### 4.2 公开销售单展示规则

公开页面不需要登录，但必须只通过 token 访问。

建议展示：

- 三行品牌抬头：`贵州酱酒馆`、`茅台集团茅乡酱酒体验馆`、`销售单`。
- 系统单号 `orderNo`。
- 下单日期。
- 客户姓名。
- 订单客户快照中的完整客户电话。
- 由省、市、区和详细地址组合的完整收货地址。
- 酒品明细：品名、数量、配送选择。
- 订单状态。
- 配送方式、快递方式、快递单号。
- 最新运输状态、当前地点、最新物流动态、轨迹发生时间和查询更新时间。
- 自带显示“自带，无物流信息”；邮寄但未录单号显示“待寄出，运单号待录入”。
- 底部售后联系方式：`177-8530-5984`。

不展示：

- 销售单号、旅行团信息和销售人员。
- 单价、小计、订单总额、货到付款金额。
- 开票状态和订单备注。
- 客户财务标记、订单财务标记。
- 财务备注、库管备注。
- 运费成本、扣酒成本、提成、积分。
- 操作日志。
- 内部用户 ID。

公开扫码页必须使用专用 public DTO，禁止直接返回内部销售单 DTO。公开 DTO 的
`customer` 仅包含 `name`、`phone`、`fullAddress`；电话和地址完整公开是本次
明确的业务要求，不代表可以扩大其他字段范围。通用电话/地址脱敏 helper 继续
保留给其他业务使用。

### 4.3 配送与物流跟踪规则

- `SalesOrder.logisticsProviderCode` 保存物流平台编码，支持
  `shunfeng`、`annengwuliu`、`yunda`、`self_carry`、`other`。
- `logisticsMethod` 继续保存展示名称和“其他”时的具体名称，兼容历史数据。
- `logisticsNo` 仍由原 finance 接口维护；快递方式仍由 packing 接口维护，不扩大
  warehouse、finance、sales 的既有字段权限。
- 邮寄订单在打包/待寄出阶段允许暂时没有运单号；进入已寄出（当前实现对应从
  非 `packed` 进入 `packed`）前必须有快递方式和运单号，自带除外。
- 修改快递方式或运单号时，清空标准化物流缓存。
- 快递100查询使用独立 `LogisticsTrackingService` 和 provider client；
  HTML helper 不发起第三方请求。
- 同一运单默认 30 分钟使用数据库缓存。第三方失败时优先展示缓存；没有缓存时
  显示“物流信息暂未查询到，请稍后刷新”。
- 接口未配置时应用正常启动并显示“物流查询服务暂未配置”。自带、快递方式
  未选或运单号为空时不调用第三方。
- 数据库只保存标准化状态、地点、描述、轨迹时间和查询时间，不保存第三方完整
  原始响应。

### 4.4 角色权限

二维码生成：

| 角色 | 权限 |
| --- | --- |
| 管理员 | 可为任意可见订单生成、重新生成二维码 |
| 销售 | 可为自己负责或自己可见订单生成二维码 |
| 财务 | 可查看二维码信息，是否允许重新生成按业务决定；默认允许查看，不主动生成 |
| 售后 | 可查看销售单详情，不生成 |
| 老板 | 可查看，不生成 |
| 库管 | 默认不生成 |
| 前台、品鉴师 | 默认不进入二维码销售单 |

Excel 导出：

| 角色 | 权限 |
| --- | --- |
| 管理员 | 可导出销售订单和旅行团 |
| 财务 | 可导出销售订单和旅行团 |
| 老板 | 可选只读导出；如果文档口径保持“财务和管理员导出”，则不开放 |
| 其他角色 | 默认不可导出 |

建议第 5 阶段先严格按 PRD：管理员和财务可导出。

### 4.5 全局标记过滤

当 `only_show_marked_records=true`：

- 销售订单导出必须使用和 `/api/sales-orders` 一致的查询范围。
- 订单必须满足自身 `SalesOrder.financeMark=true`。
- 订单导出只按订单自身 `SalesOrder.financeMark=true` 过滤，关联旅行团标记不参与订单可见性判断。
- 旅行团导出必须使用和 `/api/travel-groups` 一致的查询范围。
- 二维码生成的鉴权查询也应遵守当前角色数据范围；公开页已持有 token，不再按当前登录用户过滤。

### 5.1 SalesOrder 新增字段

建议在 `server/api/prisma/schema.prisma` 的 `SalesOrder` 增加：

```prisma
qrCodeTokenHash   String?   @unique @map("qr_code_token_hash") @db.Char(64)
qrCodeGeneratedAt DateTime? @map("qr_code_generated_at") @db.DateTime(0)
qrCodeExpiresAt   DateTime? @map("qr_code_expires_at") @db.DateTime(0)
qrCodeRevokedAt   DateTime? @map("qr_code_revoked_at") @db.DateTime(0)
```

索引建议：

```prisma

```

- 安全迁移将旧原始 token 替换为哈希；原先无过期时间的 token 直接吊销。
- migration 必须能在测试环境 `migrate deploy`。

## 6. 后端 API 设计

### 6.1 认证销售单预览

```text
GET /api/sales-orders/:id/sales-sheet
```

用途：

- Flutter 二维码销售单页面加载订单销售单信息。
- 订单详情页生成二维码前后展示同一份 DTO。

返回建议：

```json
{
  "salesSheet": {
    "order": {},
    "items": [],
    "travelGroup": {},
    "qrCode": {
      "active": true,
      "token": null,
      "url": null,
      "generatedAt": "2026-07-01T10:00:00.000Z",
      "expiresAt": "2026-07-31T10:00:00.000Z",
      "revokedAt": null
    }
  }
}
```

权限：

- 沿用 `getSalesOrder` 的读取范围。

### 6.2 生成二维码

```text
POST /api/sales-orders/:id/qr-code
```

请求体：

```json
{
  "expiresInDays": 30,
  "regenerate": false
}
```

规则：

- `expiresInDays` 缺省时使用服务端默认值 30。
- `expiresInDays` 如传入，必须是 1 到 90 的整数。
- `regenerate=false` 且已有未过期 token 时返回 `QR_CODE_ALREADY_ACTIVE`，
  不再次暴露 bearer 值。
- `regenerate=true` 时替换 token 哈希并写脱敏操作日志，旧 token 立即失效。
- 写入 `qrCodeTokenHash`、`qrCodeGeneratedAt`、`qrCodeExpiresAt` 并清空吊销时间。

返回：

```json
{
  "salesSheet": {},
  "qrCode": {
    "token": "...",
    "url": "https://example.com/api/public/sales-sheets/...",
    "expiresAt": "2026-07-31T10:00:00.000Z"
  }
}
```

### 6.3 吊销二维码

```text
DELETE /api/sales-orders/:id/qr-code
```

规则：

- 沿用二维码生成接口的角色和订单数据范围。
- 清空当前 token 哈希并记录吊销时间；旧链接立即返回统一 404 页面。
- 操作日志不记录 bearer 值或完整哈希。

### 6.4 公开扫码页

```text
GET /api/public/sales-sheets/:token
```

实现建议：

- 直接返回移动端友好的 HTML。
- 由于全局 `ApiResponseInterceptor` 会包 JSON，建议在 controller 中使用 `@Res()` 直接 `response.type('html').send(html)`。
- HTML 使用后端字符串模板即可，不引入前端构建。
- 所有动态文本必须 HTML escape。
- 不返回内部字段。
- token 不存在、过期、吊销、订单不存在时返回相同的友好 HTML 和 HTTP 404。
- 成功和错误响应统一设置 `no-store`、`no-referrer`、`nosniff` 和禁止
  framing/外部资源的 CSP，并设置禁止索引/跟踪/归档的响应头和 robots meta。

### 6.5 销售订单 Excel 导出

```text
GET /api/sales-orders/export.xlsx
```

查询参数：

- 复用 `/api/sales-orders`：`dateFrom`、`dateTo`、`query`、`customerId`、`customerPhone`、`travelGroupId`、`orderType`、`status`、`deliveryType`、`packingStatus`、`financeMark`、`customerFinanceMark`、`salesUserId`。

权限：

- `admin`、`finance`。

实现建议：

- 后端使用 `exceljs` 生成 `.xlsx`。
- controller 使用 `@Res()` 直接发送 buffer，避免被 JSON interceptor 包装。
- 文件名建议：`sales-orders-YYYYMMDD-HHmmss.xlsx`。
- 单次导出建议限制最大行数，例如 5000 行；超过返回明确错误，引导缩小筛选范围。

字段建议：

| Excel 列 | 来源 |
| --- | --- |
| 系统单号 | `orderNo` |
| 销售单号 | `salesFormNo` |
| 订单日期 | `orderDate` |

| 旅行团号 | `travelGroup.groupNo` |
| 旅行社 | `travelGroup.travelAgency` |
| 销售人员 | `salesUser.name` 或 DTO 中已有销售名称 |
| 酒品明细 | 多明细合并，例如 `品名 x 数量` |
| 配送摘要 | `deliverySummary` |
| 订单总额 | 元，保留两位 |
| 货到付款金额 | 元，保留两位 |
| 订单状态 | 中文标签 |
| 客户标记 | 已标记/未标记 |
| 订单标记 | 已标记/未标记 |
| 打包状态 | 中文标签 |
| 物流方式 | `logisticsMethod` |
| 物流单号 | `logisticsNo` |
| 运费 | 元，保留两位 |
| 是否需要开票 | 是/否 |
| 是否已开票 | 是/否 |
| 创建时间 | `createdAt` |

## 7. Flutter 客户端开发

### 7.1 依赖建议

建议新增：

```yaml
dependencies:
  qr_flutter: ^4.1.0
  path_provider: ^2.1.5
```

说明：

- `qr_flutter` 用于在 App 内渲染二维码。
- `path_provider` 用于把 Excel 文件保存到应用文档目录或下载目录附近。
- 如需要“保存销售单图片”，后续可再评估 `screenshot` 或平台保存能力；第 5 阶段验收以扫码和拍照留存为准。

- 支持 token。
- 返回 bytes、contentType、文件名。
- 非 2xx 时尽量解析 JSON 错误；解析失败则返回 HTTP 错误。

## 9. 测试计划

### 9.1 后端测试

必须覆盖：

- `SalesOrder` 二维码字段 migration 和 Prisma generate。
- 生成 token 成功。
- 缺省生成使用 30 天过期时间，最大值不能超过 90 天。
- 已有 token 未过期时要求显式重新生成。
- `regenerate=true` 时替换 token，旧 token 立即失效。
- 吊销后旧 token 立即失效。
- 有效期参数非法时报错。
- 销售不能给别人的不可见订单生成二维码。
- 公开页 token 不存在、过期和吊销返回同一 404 页面。
- 公开页不展示内部字段。
- 公开 DTO 包含完整电话、完整地址和允许展示的物流信息，但不包含金额、旅行团、
  销售人员、开票、财务/库管备注、财务标记或数据库 ID。
- 逐项断言公开页缓存、referrer、nosniff 和 CSP 响应头。
- 公开页 HTML escape，避免客户姓名、备注等字段注入 HTML。
- 销售订单导出权限：admin/finance 成功，其他角色失败。
- 旅行团导出权限：admin/finance 成功，其他角色失败。
- 导出复用列表筛选和全局标记过滤。
- 导出字段包含页面核心字段。
- 写操作进入 `operation_logs`，至少覆盖二维码生成/重新生成。

### 9.2 Flutter 测试

必须覆盖：

- `SalesSheetRecord` JSON 解析。
- `ApiClient` 文件下载成功和错误处理。
- 二维码销售单页面加载、空状态、错误状态、生成成功状态。
- 订单详情中二维码按钮的角色可见性。
- 订单导出按钮只对 admin/finance 可见。
- 旅行团导出按钮只对 admin/finance 可见。
- 导出下载成功后展示保存路径。

### 9.3 云服务器 smoke test

只在确认测试库后执行：

1. 执行 `prisma migrate deploy`。
2. 执行 seed。
3. 销售登录，选择一张 smoke 订单生成二维码。
4. 用二维码 URL 在手机浏览器打开公开销售单。
5. 确认公开页能拍照留存，且不显示内部财务/库管字段。
6. 重新生成二维码，确认旧链接失效或按设计不可继续访问。
7. 财务登录，按订单列表当前筛选导出 Excel。
8. 财务登录，按旅行团列表当前筛选导出 Excel。
9. 开启全局标记过滤，确认订单导出只按订单自身标记过滤，旅行团导出只按旅行团自身标记过滤。
10. 管理员恢复全局标记过滤。
11. 查看操作日志，确认二维码生成记录存在。

## 10. 验收标准

- 销售可以从订单生成真实二维码。
- 客人可以扫码打开公开销售单详情。
- 公开销售单在手机浏览器展示清晰，适合拍照保存。
- 二维码链接不可猜，过期逻辑可用。
- 财务和管理员可以导出销售订单 Excel。
- 财务和管理员可以导出旅行团 Excel。
- Excel 字段和页面显示核心字段一致。
- 导出遵守角色权限、当前筛选条件和全局标记过滤。
- 后端测试、Flutter 测试通过。
- 云服务器测试库 smoke 通过并形成验收记录。

## 11. 已确认的安全规则与待确认业务项

- 二维码默认 30 天、最长 90 天，禁止永久有效。
- 公开页按本次业务确认展示完整电话、完整地址和标准化物流信息；仍按最小化原则
  排除金额、旅行团、销售人员、开票、财务/库管备注和数据库 ID。
- 吊销或重新生成二维码后旧链接立即失效。
- 财务以外老板是否允许导出：文档默认只开放管理员和财务。
- 是否需要保存销售单图片：本阶段先不强制，客户拍照留存即可。
