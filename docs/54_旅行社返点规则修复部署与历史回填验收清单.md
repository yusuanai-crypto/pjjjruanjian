# 旅行社返点规则修复：部署、历史回填与验收清单

## 一、禁止事项

- 不得在未确认目标环境、未完成可恢复备份时执行任何数据库迁移或历史回填写入。
- 不得在本地或测试命令中自动连接、迁移生产数据库。
- 不得为兼容未迁移数据库而删除 `workflowStatus`、`pointsDestination`、`paymentDetails` 等当前代码需要的字段查询。
- 不得删除历史返点规则、积分记录、已确认/已返款记录或旅行团财务汇总。

## 三、确认环境和备份后的部署顺序

1. 记录目标环境、数据库主机、数据库名、当前版本和部署人。
2. 完成可恢复备份，并实际确认备份文件及恢复方案。
3. 在确认的目标环境按顺序执行：

```powershell
npx.cmd prisma migrate deploy
npx.cmd prisma generate
npm run build
```

4. 重启 API，确认启动日志没有 `DATABASE_SCHEMA_MISMATCH` 或 Prisma 缺字段错误。
5. 再执行积分表“重新计算” smoke；至少选择一个有有效规则且未返款的旅行团，以及一个已返款旅行团验证保护逻辑。

## 四、历史名称规则回填

脚本默认是零写入 dry-run。先在 `server/api` 目录执行并保存报告：

```powershell
npm run backfill:agency-rebate-rule-agency-ids -- --environment staging --database jiangjiu --report .tmp/agency-rebate-backfill.json
```

检查报告中的：

- `plannedUpdates`：仅允许规范化名称唯一匹配的规则；
- `manualReview`：无匹配、多候选或缺名称的规则必须人工处理，不得猜测；
- `alreadyBoundRuleCount`：已有 `agency_id` 的记录只统计，不覆盖。

只有在目标环境再次确认、可恢复备份完成、dry-run 报告经过审核后才允许：

```powershell
npm run backfill:agency-rebate-rule-agency-ids -- --apply --environment staging --database jiangjiu --confirmed-backup --report .tmp/agency-rebate-backfill-applied.json
```

脚本写入使用 `WHERE id = ? AND agency_id IS NULL`，并在单一事务中执行；并发变化会使事务回滚。脚本不会删除任何规则、积分记录或财务汇总。

## 五、积分表 smoke 验收

- 同一订单日期命中一条有效旅行社返点规则时，日返和月返两条记录同时生成或更新。
- 仅有可唯一匹配的历史名称规则时能够补算，并出现 `agency_name_legacy_fallback` 中文提示。
- 规则冲突时出现 `ambiguous_agency_rebate_rule`，日返/月返均不生成，不得静默按 0。
- 没有规则时明确显示旅行团/订单及缺规则原因。
- 日返已返、月返已返、扣酒已确认或人工维护时，受保护金额不被覆盖，并显示具体跳过原因。
- 订单计算失败与旅行团汇总刷新失败必须分别提示。
