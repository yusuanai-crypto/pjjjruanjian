# 第 4 阶段客户和销售订单开发文档

版本：v0.1
状态：根据 `docs/06_开发阶段计划.md` 的第 4 阶段目标整理。进入开发前如客户、物流、开票或订单状态口径有变化，先改本文再改代码。
测试环境基线：第 3 阶段文档已提示云服务器写入型 smoke 尚未闭环；第 4 阶段可先做本地开发和方案设计，涉及云端 migrate、seed、写入 smoke 前必须确认远端连接的是测试库。

## 1. 阶段目标

第 4 阶段目标是把“客户和销售订单”从当前已有的基础订单接口和页面，推进到可真实录入、查询、关联旅行团、按角色处理物流/财务/售后查询，并能支撑后续二维码销售单、售后、提成、统计的核心业务模块。

本阶段完成后应具备：

- 销售可创建订单，并能选择或新建客户。
- 客户独立成表，客户标记信息默认 false，由财务或管理员维护。
- 订单必须有订单明细，支持一个订单多个酒品。
- 旅行团订单可关联第 3 阶段的旅行团。
- 订单保存客户快照，避免客户资料后续修改影响历史订单。
- 订单支持自带、邮寄、收款明细和订单状态；`cashOnDeliveryAmountCents` 仅作为由代收明细反算的兼容字段。
- 售后可通过姓名、电话、订单号查询订单。
- 财务可查看订单金额、逐条收款明细、代收到账确认、物流单号、运费、开票状态，并可维护客户标记。
- 库管可查看待发货订单，维护物流方式、打包状态、打包件数。
- 全局“只查询已标记信息”开启后，订单查询只判断订单自身 `financeMark`；客户和旅行团查询分别判断各自标记。

## 2. 本阶段不做的事

- 不做真实二维码销售单生成和扫码页面；这是第 5 阶段。
- 不做订单 Excel 导出；这是第 5 阶段。
- 不做完整售后单、退货收货、补发、退款流程；第 4 阶段只保证售后能查订单和必要的订单状态入口。
- 不做提成、积分、旅行社返积分计算；这是第 7 阶段。
- 不做完整库存进销存、批次、成本、库存扣减；库管只围绕订单打包和物流工作。
- 不接商品库；酒品名称继续文本录入，后续如需要再独立商品模块。
- 不做 AI 查询订单；这是第 9 阶段。
- 不连接生产库，不覆盖生产数据。

## 3. 当前基线和差距

### 3.1 已有能力

根据现有文档和当前代码：

- `sales_orders` 已落库。
- `sales_order_items` 已落库。
- `/api/sales-orders` 已有列表、新建、详情、财务标记接口。
- 当前订单直接保存 `customerName`、`customerPhone`、地址字段，没有独立 `customers` 表。
- 当前订单明细已有 `productName`、`quantity`、`unitPriceCents`、`deliveryType`。
- 当前 Flutter 订单录入页已能调用 `createSalesOrder` 保存订单。
- 当前 Flutter 订单管理页已能读取 `/api/sales-orders`，财务可调用订单财务标记接口。
- 当前财务概览已能读取近期订单。
- 当前库管打包页、售后开单页仍以 UI 骨架和假数据为主。

### 3.2 关键差距

第 4 阶段需要补齐：

- 独立 `customers` 表和 `SalesOrder.customerId` 关联。
- 从旧订单冗余客户字段回填客户表和 `customerId` 的兼容迁移。
- 客户列表、客户详情、客户搜索、客户标记接口。
- 订单创建时选择已有客户或新建客户，并写入客户快照。
- 订单查询按客户、电话、订单号、旅行团、日期、状态、配送和打包状态筛选。
- 订单修改接口，按角色限制可修改字段。
- 财务字段：物流单号、运费、是否已开票、财务备注。
- 库管字段：物流方式、打包状态、打包件数、库管备注。
- 售后查询入口：姓名、电话、订单号搜索。
- 全局标记过滤按业务实体独立判断：客户看 `Customer.financeMark`，订单看 `SalesOrder.financeMark`，旅行团看 `TravelGroup.financeMark`。

## 5. 核心业务对象

### 5.1 客户 `Customer`

客户是购买的人。客户独立保存后，售后可以按姓名、电话快速定位，销售可以复用历史客户，老板和财务统计时也可以识别复购。

客户资料允许更新，但订单保存下单时的客户快照，历史订单不被客户资料变更反向影响。

### 5.2 销售订单 `SalesOrder`

销售订单是客户某一次购买记录。订单是财务、库管、售后、提成、统计共同使用的数据中心。

旅行团订单必须关联旅行团；非旅行团订单可以不关联旅行团，但仍要有客户和订单明细。

### 5.3 订单明细 `SalesOrderItem`

订单明细保存具体酒品。一个订单可以有多条明细，每条明细有酒品名称、数量、单价、配送选择和小计。

第 4 阶段不接商品库，`productName` 仍为文本。

### 5.4 旅行团关联

`orderType=travel_group` 的订单应关联 `travelGroupId`。保存后：

- 订单详情返回旅行团概要。
- 旅行团详情继续返回订单概要。
- 旅行团“是否出单”和品鉴师待总结规则以有效订单为准。
- 有效订单状态为 `valid` 或 `partial_refund`；`refunded`、`cancelled` 不算有效出单。

明细更新规则：

- 订单创建时至少 1 条有效明细。

- 修改明细必须写操作日志。
- `totalAmountCents` 以后端根据明细计算为准，除非已有兼容字段必须接收前端总额。

## 7. 枚举和业务规则

### 7.1 订单类型

沿用当前枚举：

```text
travel_group  旅行团订单
buyback       回购订单
external      外销订单
internal      内购订单
after_sales   售后订单
```

第 4 阶段主路径是 `travel_group`。其他类型保留，但不做复杂业务扩展。

### 7.2 订单状态

```text
valid           有效
partial_refund  部分退款
refunded        已退单
cancelled       取消
```

规则：

- 新建订单默认 `valid`。
- `valid` 和 `partial_refund` 算有效订单。
- `refunded` 和 `cancelled` 不算有效订单。
- 第 4 阶段只做订单状态字段和简单修改入口，不做完整售后单流转。
- 订单状态变化要影响旅行团订单概要和品鉴师待总结判断。

### 7.3 配送选择

```text
self_pickup  自带
shipping     邮寄
```

规则：

- 销售在每条订单明细选择自带或邮寄。
- 任一明细为 `shipping` 时，订单进入库管可见的发货/打包范围。
- 全部明细为 `self_pickup` 时，库管默认不作为待发货订单处理。

### 7.4 打包状态

```text
pending   待打包
packing   打包中
packed    已打包
abnormal  异常
```

规则：

- 新建含邮寄明细的订单默认 `pending`。
- 全部自带订单可默认 `packed` 或 `pending`，开发前需业务确认；本文建议默认 `packed`，避免自带订单挤入库管待发货。
- 库管和管理员可改打包状态。
- 物流方式、打包件数、库管备注由库管维护。

### 7.5 物流和开票

规则：

- 物流方式由库管选择。
- 物流单号和运费由财务维护。
- 是否需要开票由销售或售后填写。
- 是否已开票由财务维护。
- 运费、物流单号、开票状态变更必须写操作日志。

## 8. 财务标记和全局查询规则

### 8.1 客户财务标记

客户 `financeMark` 默认 `false`。

固定规则：

- 财务、管理员可标记或取消标记客户。
- 标记或取消标记后记录本次操作的 `markedById`、`markedAt`。
- 当前是否已标记只以 `financeMark` 判断；`markedById`、`markedAt` 只表示最后一次标记操作审计信息。
- 客户资料修改后不自动取消标记，只写操作日志。
- 客户、订单、旅行团在全局标记过滤中分别判断自身 `financeMark`。

### 8.2 订单财务标记兼容

当前 `sales_orders.finance_mark` 已存在，并被旧订单查询和财务标记接口使用。第 4 阶段保留该字段，作为订单确认状态或历史兼容字段。

原则：

- 新增客户表后，不能继续只用 `sales_orders.finance_mark` 代表客户已确认。
- `/api/sales-orders/:id/finance-mark` 可保留，避免旧页面和测试立刻失效。
- 新增 `/api/customers/:id/finance-mark` 作为客户标记主接口。
- 页面上应清楚区分“客户标记”和“订单标记”，避免财务误判。

### 8.3 全局标记过滤

当 `system_settings.only_show_marked_records = true` 时：

- 客户查询只返回 `customers.financeMark = true`。
- 订单查询只返回订单自身 `SalesOrder.financeMark = true` 的订单。
- 关联客户或旅行团的标记不参与订单可见性判断；客户、旅行团查询仍分别判断自身 `financeMark`。
- 旅行团详情中的订单概要也必须过滤未通过标记规则的订单。
- 财务导出、老板统计、售后查询和后续 AI 查询都应使用同样过滤规则。
- 管理员恢复开关后，系统按角色权限正常查询。

## 9. 角色权限定版

| 角色 | 可看 | 可改 |
| --- | --- | --- |
| 管理员 | 全部客户、全部订单 | 全部字段、客户标记、订单标记 |
| 老板 | 全部客户和订单，只读，受全局标记过滤影响 | 不可修改 |
| 前台 | 默认不进入订单管理；如保留兼容读权限，应受全局标记过滤 | 不可修改订单和客户 |
| 销售 | 自己创建或归属自己的客户和订单；可搜索可关联旅行团 | 新建订单、维护自己订单的客户基础信息、明细、配送、货到付款、是否需要开票 |
| 财务 | 全部订单金额、货到付款、物流费用、开票、标记 | 客户标记、订单标记、物流单号、运费、是否已开票、财务备注、订单状态 |
| 库管 | 邮寄订单和待打包订单 | 物流方式、打包状态、打包件数、库管备注 |
| 售后 | 客户和订单查询 | 第 4 阶段可修改订单状态和售后备注类字段；完整售后单第 6 阶段开发 |
| 品鉴师 | 不进入订单管理 | 不可修改 |

字段权限建议：

- 销售不能改财务字段、库管字段、客户标记、订单标记。
- 财务不能修改订单明细数量和单价，除非管理员授权。
- 库管不能修改金额、客户标记、订单状态。
- 售后不能修改金额、物流费用、客户标记。
- 未授权字段应返回明确错误，不要静默忽略。

- `delivery_type` 已存在，继续使用。

### 10.5 回填策略

回填旧订单客户：

1. 按 `customer_phone + customer_name` 聚合旧订单。
2. 电话为空时按 `customer_name + address` 尽力创建客户，但标记为未确认。
3. 为每个聚合结果创建 `customers` 记录。
4. 回填 `sales_orders.customer_id`。
5. 不覆盖订单快照字段。
6. 回填过程写 migration 或幂等脚本，必须可重复检查，不能重复造客户。

### 11.3 创建订单请求

建议请求：

```json
{
  "orderType": "travel_group",
  "orderDate": "2026-06-29",
  "customerId": "optional-existing-customer-id",
  "customer": {
    "name": "张女士",
    "phone": "13800000000",
    "province": "贵州省",
    "city": "贵阳市",
    "district": "观山湖区",
    "address": "测试地址 1 号"
  },
  "travelGroupId": "travel-group-id",
  "salesFormNo": "manual-form-no",
  "cashOnDeliveryAmountCents": 10000,
  "invoiceRequired": false,
  "remark": "客户希望尽快发货",
  "items": [
    {
      "productName": "酱香珍藏",
      "quantity": 2,
      "unitPriceCents": 39900,
      "deliveryType": "shipping",
      "notes": "礼盒装"
    }
  ]
}
```

规则：

- `customerId` 和 `customer` 至少提供一个。
- 如果提供 `customerId`，后端读取客户并写入订单客户快照。
- 如果提供 `customer`，后端先创建客户，再创建订单。
- `orderType=travel_group` 时 `travelGroupId` 必填。
- `items` 至少一条，`productName` 必填，`quantity > 0`。
- 订单号由系统生成，前端不传或传了也忽略。
- 创建、客户创建、明细保存、旅行团汇总更新必须在一个事务中。
