# 项目目录结构

本文设计未来项目代码的目录结构。目录结构不是越复杂越好，第一版要清晰、容易找文件、方便以后扩展。

推荐根目录：

```text
jiangjiu/
  apps/
    mobile_desktop/
  server/
    api/
  packages/
    shared/
  deploy/
  docs/
  README.md
```

为什么这样分：

- `apps/` 放员工实际使用的软件。
- `server/` 放云服务器后端。
- `packages/` 放前后端共用的类型和工具。
- `deploy/` 放部署配置。
- `docs/` 放产品和技术文档。

## 1. Flutter 客户端目录

```text
apps/
  mobile_desktop/
    lib/
      main.dart
      app/
      core/
      features/
      shared/
    assets/
    test/
    pubspec.yaml
```

### 1.1 `lib/main.dart`

App 入口文件。

为什么需要：

所有 Flutter 应用都从入口启动。这里负责启动 App、加载配置、进入登录页或首页。

### 1.2 `lib/app/`

放 App 级别配置。

建议内容：

```text
app/
  app.dart
  router.dart
  theme.dart
```

用途：

- `app.dart`：App 主组件。
- `router.dart`：页面路由。
- `theme.dart`：颜色、字体、按钮样式。

为什么需要：

把全局设置集中管理，后面修改主题或页面跳转不会到处找代码。

### 1.3 `lib/core/`

放基础能力。

建议内容：

```text
core/
  api/
  auth/
  config/
  storage/
  errors/
```

用途：

- `api/`：请求后端接口。
- `auth/`：登录状态和权限。
- `config/`：服务器地址等配置。
- `storage/`：本地保存登录 token。
- `errors/`：统一错误处理。

为什么需要：

这些能力每个模块都会用到。如果散落在各个页面，后期维护会很麻烦。

### 1.4 `lib/features/`

放业务模块。

建议内容：

```text
features/
  login/
  dashboard/
  travel_groups/
  guides/
  customers/
  sales_orders/
  order_qrcodes/
  after_sales/
  finance/
  warehouse/
  commissions/
  analytics/
  ai_assistant/
  settings/
```

为什么按功能拆：

每个业务模块有自己的页面、表单、接口调用和状态。按功能放在一起，新人也容易理解。

### 1.5 `lib/shared/`

放通用组件。

建议内容：

```text
shared/
  widgets/
  models/
  utils/
```

用途：

- `widgets/`：通用按钮、表格、筛选框。
- `models/`：客户端数据模型。
- `utils/`：日期格式化、金额格式化等。

为什么需要：

比如日期选择、搜索框、金额显示很多页面都会用，统一封装可以减少重复代码。

## 2. 后端 API 目录

```text
server/
  api/
    src/
      main.ts
      app.module.ts
      modules/
      common/
      prisma/
      ai/
    prisma/
      schema.prisma
      migrations/
    test/
    package.json
```

### 2.1 `src/modules/`

放后端业务模块。

建议内容：

```text
modules/
  auth/
  users/
  travel_groups/
  guides/
  customers/
  sales_orders/
  after_sales/
  finance/
  warehouse/
  commissions/
  analytics/
  settings/
```

为什么这样拆：

后端模块和 App 业务模块对应，沟通起来简单。例如 App 的“旅行团管理”对应后端的 `travel_groups` 模块。

### 2.2 `src/common/`

放通用后端能力。

建议内容：

```text
common/
  guards/
  decorators/
  filters/
  pipes/
  utils/
```

用途：

- 权限检查
- 参数校验
- 错误处理
- 日期和金额工具

为什么需要：

登录权限、错误提示、参数检查是所有接口都要用的，集中管理更安全。

### 2.3 `src/prisma/`

放数据库连接服务。

为什么需要：

所有模块都通过统一 Prisma 服务访问数据库，避免每个模块各写一套数据库连接。

### 2.4 `src/ai/`

放 AI 查询和建议相关代码。

为什么单独放：

AI 有权限检查、数据查询、提示词组织、回答生成等逻辑。单独管理，避免混进普通订单代码里。

## 3. 共享包目录

```text
packages/
  shared/
    src/
      types/
      constants/
      validators/
    package.json
```

用途：

- 共享角色名称
- 共享订单状态
- 共享快递方式
- 共享部分类型定义

为什么需要：

例如快递方式有“自带、韵达、安能、顺丰”。如果前端写一份、后端写一份，后期改名称容易不一致。共享包可以减少这种错误。

## 4. 部署目录

```text
deploy/
  docker-compose.yml
  nginx/
  scripts/
    backup-db.sh
    restore-db.sh
```

用途：

- `docker-compose.yml`：启动后端、数据库、Nginx。
- `nginx/`：HTTPS 和转发配置。
- `backup-db.sh`：数据库备份脚本。
- `restore-db.sh`：数据库恢复脚本。

为什么需要：

上线不是把代码写完就结束。部署、备份、恢复同样重要。特别是业务数据，一定要能备份和恢复。

## 5. 文档目录

```text
docs/
  01_PRD.md
  02_功能模块拆分.md
  03_技术选型建议.md
  04_项目目录结构.md
  05_数据库初步设计.md
  06_开发阶段计划.md
```

为什么需要：

文档可以让老板、员工、开发者对系统理解一致。尤其是统计口径、权限、提成规则，必须先写清楚。

## 6. 第一版目录不要过度复杂

第一版不建议：

- 一开始拆多个后端服务。
- 一开始做多个 App 项目。
- 一开始建很多无用公共包。
- 一开始做复杂插件系统。

推荐做法：

- 一个 Flutter App。
- 一个后端 API。
- 一个 MySQL 数据库。
- 一套部署配置。

为什么：

项目越简单，越容易上线。等业务跑起来后，再根据真实需求拆分和扩展。
