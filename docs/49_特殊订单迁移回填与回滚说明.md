# 特殊订单迁移、历史回填与回滚说明

## 上线顺序

1. 先备份数据库并在影子库执行 `20260729000200_special_orders_workflow`。
2. 运行 `npx prisma validate` 和应用构建；本迁移只扩展表结构，不更新历史业务行。
3. 在影子库运行 `npm run preflight:special-orders`。脚本只读，输出历史 `INTERNAL`、`EXTERNAL`、`BUYBACK` 订单及其库存、收款、售后、提成下游事实。
4. 由财务、仓库和业务负责人逐单确认历史状态及方向，再生成经审批的回填清单。
5. 先灰度服务端，再灰度 Flutter。新接口仅识别 `workflow_status IS NOT NULL` 的特殊订单；历史空值订单继续走原接口，避免改变旅行团、售后和普通订单行为。

## 为什么不自动把历史订单标为草稿

历史订单可能已经完成出入库、收付款、售后或提成。缺少新工作流事件不代表未生效，因此迁移不得把所有历史行统一设为 `DRAFT`。预检分类只作为人工核对线索：

- `CANCELLED_CANDIDATE`：旧状态已取消，仍需确认是否存在冲销遗漏。
- `MANUAL_REVIEW_EFFECTIVE_OR_REVERSED`：发现下游事实，必须核对原始凭证后决定 `APPROVED`、`COMPLETED` 或保持历史兼容。
- `MANUAL_REVIEW_NO_DOWNSTREAM_FACT_FOUND`：没有发现下游事实，也不能据此自动推断为草稿。

## 经审批的回填原则

- 每笔回填必须包含目标状态、工作流版本、审批人、理由和来源凭证编号。
- 已生效历史单先核对库存方向：内购/外销为销售出库和应收，回购为采购入库和应付。
- 发现旧回购被计入应收、销售收入、毛利、提成、积分或返点时，使用独立纠正/冲销凭证，不删除原流水。
- 审批事件从回填时点追加 `CREATED` 和代表当前事实的事件；不得伪造历史操作时间或覆盖既有日志。
- 序列化回购只有在逐瓶真实物流码可核实时才允许纳入新库存账；禁止补造虚拟物流码。
- 回填 SQL 或脚本应从经签字的清单生成，先支持 dry-run、逐单幂等键和影响行数校验，再单独评审；本变更不附带自动写入脚本。

## 回滚

- 优先回滚应用流量到不写新字段的兼容版本，并停止新特殊订单写入。
- 已产生的库存、结算、付款和审批事件不得物理删除；需要撤销时调用反审核，生成冲销凭证。
- 扩展列和新表暂时保留，不执行 `DROP`。确认没有旧版本冲突后再制定独立、经备份验证的收缩迁移。
- 若迁移或灰度失败，保留预检报告、幂等键和操作日志供对账，不运行 seed、清库或生产数据库重置。
