# 订单收款明细开发、迁移与回滚说明

更新日期：2026-07-29

## 1. 当前实现范围

订单收款已从单一 `cashOnDeliveryAmountCents` 兼容列升级为以下模型：

- `PaymentMethod`：财务维护的收款方式主数据，支持新增、改名、分类、启停、排序和设置默认，不提供物理删除。
- `SalesOrderPaymentDetail`：订单级收款事实，保存方式名称和分类快照、整数分金额、排序及代收到账确认。
- `SalesOrder`：新增完成时间/完成人及收款明细锁定、解锁审计字段，不修改 `SalesOrderStatus`。

收款金额允许正数、`0` 和负数。同一订单至少一条明细，同一方式可以重复，所有明细金额合计必须严格等于服务端按商品快照计算的订单总额。

## 2. 数据权威与兼容口径

`sales_order_payment_details` 是新口径的订单收款权威数据。`sales_orders.cash_on_delivery_amount_cents` 暂时保留，定义为所有分类快照为 `collect_on_delivery` 的明细金额有符号合计。

兼容规则如下：

1. 新客户端传 `paymentDetails` 时完全以明细为准，忽略同一请求中的旧货到付款金额。
2. 老客户端未传 `paymentDetails` 时，后端把 `cashOnDeliveryAmountCents` 拆成“货到付款”和默认即时收款两条兼容明细；金额为 `0` 时只保留默认即时收款。
3. 每次新建或替换明细都在同一事务内反算兼容列。
4. 查询、旅行团汇总、导游积分、财务指标、客户最近订单、AI 查询和销售单优先按明细分类快照求和；只有没有明细的迁移过渡数据才回退兼容列。
5. Flutter 在旧后端没有返回 `paymentDetails` 或 `paymentSummary` 时，继续从订单总额和兼容列构造只读汇总。

历史明细始终显示 `paymentMethodNameSnapshot` 和 `paymentMethodCategorySnapshot`。方式改名或停用不会改写历史快照；已停用方式只能在保留原明细 ID 且方式未改变时继续保存，不能作为新明细加入。

## 3. 相关模块审计结论

| 模块 | 当前口径 |
| --- | --- |
| 旅行团订单汇总 | 收款明细分类快照优先，兼容列兜底 |
| 旅行团财务汇总 | 收款明细分类快照优先，支持负数冲销 |
| 导游积分汇总 | 收款明细分类快照优先，已付订金按订单总额减代收有符号计算 |
| 财务工作台/统计 | 代收金额按收款明细求和 |
| 每日对账 | 应收按订单总额和已确认退款；`reconciliation_payment_methods` 仍是财务手工录入的实际到账事实，与收款方式主数据不是同一张表 |
| AI 查询 | 只读订单 DTO 的收款明细优先，兼容列兜底 |
| 售后订单 | 生成独立销售订单时同步创建合法默认收款明细 |
| 操作日志 | 方式维护、明细替换、确认重置、完成、锁定、解锁、代收确认均记录前后数据 |
| 库存 | 仍只由商品、数量、履约状态和库存版本驱动；收款字段不参与库存数量计算 |
| 二维码/公开销售单/打印 | 使用订单收款名称和分类快照逐行展示 |
| Excel | 一条收款明细一行，订单字段重复，金额保持数值单元格 |
| 隐藏未标记信息 | 仍只读取各业务对象的 `financeMark` 和全局 `onlyShowMarkedRecords`；未关联收款方式或收款明细 |

## 4. 生产迁移步骤

本地实现只提供迁移文件，不自动执行生产部署。

迁移文件：

`server/api/prisma/migrations/20260729000100_sales_order_payment_details/migration.sql`

建议顺序：

1. 进入维护窗口，暂停订单新增、订单修改、售后建单和收款确认写入。
2. 备份 MySQL，至少导出 `users`、`sales_orders` 以及全部 Prisma migration 记录；记录备份时间和恢复演练结果。
3. 在与生产同版本的临时库执行迁移，记录耗时、表锁时间、回填行数和核验 SQL 结果。
4. 构建并验证兼容新旧请求的 NestJS 版本。
5. 在生产 API 目录执行 `npx prisma migrate deploy`。
6. 执行本节核验 SQL。存在不一致时不要恢复写流量。
7. 发布后端，再恢复订单写入；观察错误码、事务回滚和慢查询。
8. 后端稳定后再发布 Flutter 客户端。老客户端可以在过渡期继续使用兼容字段。

迁移会初始化六种稳定 code：

| code | 名称 | 分类 | 默认 |
| --- | --- | --- | --- |
| `shouqianba` | 收钱吧 | `direct_receipt` | 是 |
| `boc_pos` | 中行POS机 | `direct_receipt` | 否 |
| `ceb_pos` | 光大POS机 | `direct_receipt` | 否 |
| `cash` | 现金 | `direct_receipt` | 否 |
| `cash_on_delivery` | 货到付款 | `collect_on_delivery` | 否 |
| `bank_transfer` | 转账 | `direct_receipt` | 否 |

## 5. 迁移后核验 SQL

以下 SQL 只读，可在恢复写流量前执行：

```sql
SELECT code, name, category, is_active, is_default, sort_order
FROM payment_methods
ORDER BY sort_order, id;

SELECT COUNT(*) AS active_default_count
FROM payment_methods
WHERE is_active = TRUE AND is_default = TRUE;

SELECT so.id, so.order_no, so.total_amount_cents,
       COALESCE(SUM(pd.amount_cents), 0) AS payment_total_cents
FROM sales_orders so
LEFT JOIN sales_order_payment_details pd ON pd.sales_order_id = so.id
GROUP BY so.id, so.order_no, so.total_amount_cents
HAVING COUNT(pd.id) = 0
    OR COALESCE(SUM(pd.amount_cents), 0) <> so.total_amount_cents;

SELECT so.id, so.order_no, so.cash_on_delivery_amount_cents,
       COALESCE(SUM(CASE
         WHEN pd.payment_method_category_snapshot = 'collect_on_delivery'
         THEN pd.amount_cents ELSE 0 END), 0) AS derived_cod_cents
FROM sales_orders so
LEFT JOIN sales_order_payment_details pd ON pd.sales_order_id = so.id
GROUP BY so.id, so.order_no, so.cash_on_delivery_amount_cents
HAVING derived_cod_cents <> so.cash_on_delivery_amount_cents;

SELECT COUNT(*) AS invalid_snapshot_count
FROM sales_order_payment_details
WHERE payment_method_name_snapshot = ''
   OR payment_method_name_snapshot IS NULL
   OR payment_method_category_snapshot IS NULL;
```

预期：

- 六种初始化方式完整；
- `active_default_count = 1`；
- 后三条异常查询返回零行或计数为 `0`。

## 6. 回滚策略

### 6.1 首选：只回滚应用，不回退数据库

本次迁移是扩展式迁移，旧字段仍保留。出现应用故障时首选：

1. 立即停止新版本写流量。
2. 回滚 Flutter 和 NestJS 到上一个已验证版本。
3. 保留新增表、字段和回填数据，不执行 `DROP`。
4. 旧后端继续读取 `cash_on_delivery_amount_cents`。回滚期间禁止用旧客户端修改已经拆成多种收款方式的订单，否则旧协议只能表达一个货到付款合计，可能把多条明细折叠。
5. 修复后重新发布新后端并再次运行核验 SQL。

该方案保留新收款明细和确认事实，恢复风险最低。

### 6.2 必须回退数据库时

仅在确认不会再次前滚、已完整备份并停止所有写入后执行：

1. 导出 `payment_methods`、`sales_order_payment_details` 以及新增完成/锁定字段。
2. 用核验 SQL确认兼容列与明细分类合计一致。
3. 先回滚应用并验证旧应用能正常读取订单。
4. 再按迁移 SQL 的反向依赖顺序移除外键、索引、`sales_order_payment_details`、`payment_methods` 和 `sales_orders` 新增列。
5. 不修改 `SalesOrderStatus`，不删除 `cash_on_delivery_amount_cents`。
6. 恢复流量后验证创建、修改、售后、旅行团汇总、库存同步、对账和二维码。

数据库破坏性回退会永久丢失多方式拆分、名称/分类快照、代收确认和完成/锁定审计，必须由 DBA 审核并从备份可恢复后才能执行。

## 8. 已知风险

- “唯一启用默认方式”由服务事务和测试保证，MySQL 当前没有额外的单行数据库约束；应监控默认方式数量。
- 大订单量环境中，生产迁移的两次历史回填会扫描 `sales_orders` 并写入一到两倍明细行，应先在同规模临时库测量锁等待和磁盘增长。
- 旧客户端修改多方式订单时无法表达完整拆分；兼容期应尽快升级客户端，并限制旧客户端修改已拆分订单。
- 数据库破坏性回滚会丢失新模型独有事实，默认只允许应用回滚。
- Prisma 6 已提示 `package.json#prisma` 配置将在 Prisma 7 移除，后续升级前应迁移到 `prisma.config.ts`。
